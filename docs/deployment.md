# Контейнеры и развёртывание ПСБ

## Область

Это инфраструктура существующей **одноразовой пакетной задачи**. Она читает `questions.csv` и `knowledge-base.zip`, обращается к настроенному LLM-прокси и записывает `submission.csv`. Входящих HTTP-портов, постоянно работающего сервера, БД и GPU у этой задачи нет.

Docker Compose описывает runtime, Ansible подготавливает выпуск на существующем Debian/Ubuntu-хосте с Docker Engine и Compose. Профиль рассчитан на системный rootful Docker без `userns-remap`: UID `10001` должен одинаково отображаться на хосте и в контейнере. Rootless/remapped daemon отклоняется; роль не ослабляет его настройки ради совместимости. Создание виртуальной машины, облачная сеть, установка Docker и финальный веб-интерфейс сюда не входят. Облако и целевой сервер должны быть выбраны отдельно; playbook не содержит настоящих адресов.

Конкурсный ZIP продолжает собираться прежним способом. Контейнерный bootstrap не входит в него и не меняет платформенный HTTP-контракт с прокси организаторов.

## Структура

| Путь | Назначение |
| --- | --- |
| `Dockerfile`, `.dockerignore` | Воспроизводимый runtime-образ и минимальный контекст сборки |
| `containers/entrypoint.py` | Проверка контейнерной конфигурации и чтение mounted secret |
| `deploy/compose.yml` | Ограничения процесса, подключения данных и результата |
| `deploy/.env.example` | Пример несекретной конфигурации; placeholders не являются выпуском |
| `infra/ansible/` | Проверка происхождения образа и подготовка конкретного Docker-хоста |
| `.github/iac/requirements.txt` | Полный hash-lock инструментов Ansible, отдельно от runtime |
| `.github/workflows/security.yml` | Проверки, сборка, SBOM и управляемая публикация |

## Границы контейнера

Образ рассчитан на `linux/amd64`. Базовый `python:3.15.0-alpine3.24` закреплён digest конкретного amd64 manifest. Обновление версии или digest проходит тот же CI, что и изменение кода. Приложение использует стандартную библиотеку; pip/ensurepip и установщики пакетов Python удалены из runtime. Каталог стандартной библиотеки определяется через `sysconfig` установленного интерпретатора, поэтому очистка не зависит от номера Python в пути. Полный набор регрессий выполняется также на Python 3.15. При сборке из подписанного репозитория Alpine устанавливаются закреплённые исправления `zlib=1.4-r0`, `musl=1.2.6-r3` и `musl-utils=1.2.6-r3`. Версия zlib дополнительно проверяется по inventory, уязвимости библиотек проверяет обязательный сканер образа.

Ненужные приложению SQLite, curses, readline, native UUID и Tk-модули удалены. ELF-зависимости оставшихся Python-модулей пересчитываются по схеме официального Python image; `apk` удаляет освободившиеся библиотеки и обновляет ведомость пакетов. CI дополнительно запрещает возвращение шести удалённых пакетов. Это устраняет известные уязвимые компоненты физически, не исключает их из отчёта.

Сканер секретов запускается без интерпретации SBOM как инвентаря пакетов (`--disabled-analyzers sbom`): в Trivy 0.76.2 этот посторонний анализатор может выдавать предупреждения даже при режиме `--scanners secret`. Файлы SBOM продолжают проверяться как текст на секреты; четвёртая preflight-фикстура требует обнаружения синтетического ключа внутри CycloneDX JSON. Проверка уязвимостей и отдельное построение SBOM сохраняют свои анализаторы. Любые неожиданные предупреждения и ошибки сканера секретов по-прежнему блокируют gate. Реализация анализатора: [Trivy 0.76.2](https://github.com/aquasecurity/trivy/blob/v0.76.2/pkg/fanal/analyzer/sbom/sbom.go), [предупреждения декодера](https://github.com/aquasecurity/trivy/blob/v0.76.2/pkg/sbom/cyclonedx/unmarshal.go).

В контекст сборки разрешены только Dockerfile и runtime-исходники. Корпус, вопросы, результаты, тестовые эталоны, `.git`, `.env` и ключи в образ не копируются. Рабочие модули и bootstrap принадлежат root и недоступны приложению для изменения.

Runtime-профиль Compose:

- UID/GID `10001:10001`, read-only корневая файловая система;
- `cap_drop: ALL`, `no-new-privileges`, стандартный seccomp Docker;
- корпус `/data` только для чтения, отдельный writable-каталог `/output`;
- `/tmp` — ограниченный tmpfs с `noexec,nosuid,nodev`;
- ограничения памяти, CPU и числа процессов, ротация логов;
- отсутствуют опубликованные порты, Docker socket, privileged и host namespaces;
- `restart: "no"`: повторный запуск не выполняется автоматически и не расходует квоту LLM;
- Python запускается с `-I -B -u`; доверенный `/app` явно добавляется в import path.

У batch-задачи нет фиктивного HTTP healthcheck. Проверяется реальный выходной CSV. Даже exit code `0` не доказывает содержательную полноту: приложение сохраняет технические ответы при достижении дедлайна, а юридическая точность оценивается отдельно.

По умолчанию выделяются 2 CPU и 2 ГиБ RAM; параметры Ansible ограничены сверху 8 CPU и 16 ГиБ. Это границы конфигурации, а не измеренная потребность любого будущего корпуса.

## Ключ и соединение с LLM

Контейнер принимает **файл** `/run/secrets/llm_api_key`, смонтированный read-only. Файл должен быть обычным, принадлежать UID `10001`, иметь права `0400` или `0600` и содержать один непустой ASCII-токен размером не более 8192 байт. Ansible требует более строгий вариант `0400` и проверяет только метаданные. Символические ссылки, FIFO, чужой владелец, доступ группы/остальных и управляющие символы отклоняются.

Секрет создаётся на целевом хосте через выбранное хранилище секретов или другой защищённый канал. Его значение не передаётся через inventory, extra-vars, `.env`, CLI-аргументы, Docker `ARG`/`ENV` или build cache. Compose содержит только путь к файлу. Обычный bind mount не является шифрованным хранилищем секретов: защиту и ротацию исходного файла обеспечивает оператор.

Bootstrap читает ключ уже внутри процесса и передаёт его существующему клиенту через окружение этого процесса. Значение не попадает в первоначальную конфигурацию `docker inspect`, но остаётся доступно приложению и администратору хоста. Все Python-модули приложения находятся в одной зоне доверия.

Для этого самостоятельного развёртывания `LLM_BASE_URL` обязан быть HTTPS URL без логина, пароля, query и fragment; модель задаётся явно через `LLM_MODEL`. Проверка сертификата остаётся включённой. Контейнерный профиль не предназначен для прямого подключения к HTTP-прокси платформы: автоматический сабмит по-прежнему использует исходный ZIP.

**Compose bridge разрешает исходящие подключения. Это не allowlist адресов.** Ограничение egress до доверенного LLM-прокси нужно реализовать и проверить в политике сети, хоста или прокси. Playbook не меняет firewall и не выдаёт отсутствие опубликованных портов за контроль исходящего трафика.

## Что блокирует сборку и выпуск

| Проверка | Проверяемый объект | Блокирующее условие |
| --- | --- | --- |
| Hadolint | Dockerfile | Warning/error, включая inline-подавления, которые CI не принимает |
| Trivy config | Dockerfile | Ошибки безопасности MEDIUM/HIGH/CRITICAL или неполный анализ |
| Trivy image | Собранный образ | HIGH/CRITICAL уязвимости из доступной БД; неподдерживаемая ОС; неполный анализ; нарушение закреплённого профиля пакетов |
| Trivy secrets | Сканируемые слои и image config/history | Любая находка, включая дополнительные AI-форматы, или ошибка сканера |
| Compose policy | Канонический Compose JSON | Нарушение обязательных ограничений, небезопасные mounts, mutable image, неожиданные сервисы/порты/права |
| Ansible | Playbook, role и зависимости контроллера | Syntax/lint/policy errors, уязвимость dependency lock |
| Container smoke | Реально запущенный образ | Нарушение изоляции, ошибка TLS/секрета/CSV или несоответствие runtime-исходников checkout |

Проверки контейнера и IaC входят в общий `Security gate` вместе с прежними Gitleaks, SAST, CodeQL, зависимостями, workflow и регрессией. Ошибка сканера не считается чистым результатом. SBOM CycloneDX создаётся отдельным вызовом: сам по себе он не заменяет сканирование уязвимостей.

У базы Alpine есть существенное [ограничение покрытия Trivy](https://trivy.dev/docs/latest/coverage/os/alpine/): её security database может ещё не содержать уязвимости без опубликованного исправления. `--ignore-unfixed` не используется, но это не добавляет отсутствующие записи в БД. Поэтому нулевой отчёт Trivy не означает отсутствие всех известных проблем. При выборе базы отдельно проверены upstream-исправления zlib и физическое удаление SQLite с известными CVE, ещё отсутствовавшими в Alpine secdb; пакетные проверки CI закрепляют эти решения. CPython, собранный из исходников в официальном image, не является APK-пакетом: этот отчёт не заменяет проверку обновлений самого Python.

Тест контейнера использует искусственные входные данные, искусственный ключ и локальную HTTPS-заглушку. Он проверяет непривилегированный процесс, реальные filesystem/capabilities/seccomp ограничения, успешный цитируемый ответ и отказ при непригодном секрете. Настоящие API провайдеров в CI не вызываются.

Trivy сохраняет находки в сканируемых нижних слоях даже после удаления файла в верхнем. При этом он может пропускать распознанные базовые слои, архивы, бинарные файлы и встроенные исключения; это не побайтовый аудит всего image. Gitleaks продолжает отдельно проверять исходники и историю. Из secret-отчётов исключаются текст совпадений, окружающий код и исходные пути.

## Управляемая публикация

Обычные PR/push/scheduled прогоны выполняют проверки. Публикация включается отдельным boolean-параметром ручного запуска `Security scans` на `main`; его значение по умолчанию — false.

После успеха общего gate publishing job получает **тот же image artifact**, который прошёл проверки, проверяет контрольные суммы и публикует его в GHCR. Повторной сборки между сканированием и публикацией нет. Для полученного registry digest создаются GitHub OIDC provenance и SBOM attestations. Долгоживущий signing key не требуется; права на registry и OIDC выдаются только publishing job.

Attestation подтверждает происхождение. Результат сканеров обеспечивается связью publishing job с общим gate; подпись не заменяет анализ образа.

Перед первым выпуском администратор задаёт требуемые ruleset/branch protection и защиту environment для публикации. Сам workflow не настраивает обязательные reviews в GitHub. Изменения Dockerfile, `containers/`, `deploy/`, `infra/`, `.github/` и правил сканеров требуют такого же внимания, как изменения приложения.

## Подготовка хоста

1. Выбрать выделенный Debian/Ubuntu-хост с Docker Engine, Docker Compose, SSH и возможностью privilege escalation. Доступ к Docker API равносилен административному доступу к хосту; пользователю приложения членство в группе Docker не нужно.
2. Подготовить controller с Python 3.13, hash-locked Ansible и актуальным `gh`, поддерживающим `attestation verify`. Настроить SSH known_hosts и доступ controller/host к GHCR отдельно.
3. После проверенного ручного выпуска взять из результата CI registry digest образа и точный source commit.
4. Подготовить входные файлы и закрытый файл секрета на хосте. Не отправлять ключ в GitHub issue, PR или переписку.
5. Выполнить Ansible с приватными inventory и несекретными параметрами развёртывания.

Установка закреплённых инструментов на controller из корня репозитория:

```bash
python3.13 -m venv .venv-iac
.venv-iac/bin/python -m pip install --require-hashes --only-binary=:all: \
  -r .github/iac/requirements.txt
```

Конкретные переменные, проверки и команды находятся в [infra/ansible/README.md](../infra/ansible/README.md). Пример inventory указывает `example.invalid`; image/source по умолчанию пустые. Эти значения намеренно не позволяют случайно развернуть непроверенный выпуск.

До `docker pull` роль проверяет attestation для конкретного digest, репозитория `Moonwuk/grounded-legal-rag`, workflow `.github/workflows/security.yml`, `refs/heads/main` и ожидаемого source commit. Самостоятельно управляемые runners не принимаются в качестве доверенного builder. Ошибка проверки либо устаревший `gh` останавливают процедуру.

Ansible проверяет всю цепочку родительских каталогов до первой записи с правами root, затем подготавливает каталоги и Compose. Символические ссылки и недоверенные владельцы служебного дерева отклоняются; read-only checks не подменяются попыткой забрать такое дерево через `chown`.

Обращения к модели playbook не запускает. Batch запускается оператором через установленный `/srv/psb/run-batch`: helper удерживает эксклюзивную блокировку, повторно проверяет конфигурацию/права, сохраняет предыдущие два выходных файла в закрытом каталоге истории и требует свежий CSV. Результат находится в назначенном output-каталоге; его следует проверять вместе со статусом конкретного запуска. Откат — повторная подготовка ранее одобренного digest и соответствующего ему commit. Данные и предыдущие результаты не являются частью образа.

## Границы проведённой проверки

CI проверяет синтаксис и политику IaC, реальную Docker-сборку и поведение контейнера. Он не подтверждает конфигурацию ещё не выбранного сервера, firewall, SSH, хранилища секретов, доступность боевого прокси или юридическую точность ответов. Выпуск в registry и применение Ansible к реальному хосту — отдельные явные действия.
