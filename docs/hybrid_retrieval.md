# Гибридный поиск: BM25 + эмбеддинги `bge-m3`, реранкер по запросу

11 ноября 2026. Модули: `psb_llm.EmbeddingClient`, `psb_retrieval.Retriever.enable_dense`,
`_dense_candidates`; подключение в `solution.py`. Регрессии —
[tests/test_dense_retrieval.py](../tests/test_dense_retrieval.py).

## Зачем

Лексический поиск находит положение по общим словам. Вопрос, заданный другими
словами («руководитель учётной службы» вместо «главный бухгалтер», «отозвал
разрешение на работу с информацией» вместо «отзыв согласия на обработку
персональных данных»), может не найти нужную норму, и ответ становится
отказом. Регламент даёт на платформе модель эмбеддингов BAAI/bge-m3 через тот
же прокси (`{LLM_BASE_URL}/embeddings`, имя модели — `EMB_MODEL`).

## Как устроено

- Включается, только если задан `EMB_MODEL`. Фрагменты базы индексируются
  партиями по 32 текста; бюджет — `PSB_DENSE_SECONDS`, по умолчанию пятая часть
  времени запуска, не более 240 с.
- После первых 128 фрагментов скорость провайдера экстраполируется: если весь
  корпус не успевает в бюджет, индексация прекращается сразу
  (`dense_disabled:embedding_too_slow`), а не тратит бюджет впустую.
- Плотные кандидаты — **резерв**, а не замена: к выдаче BM25 добавляются 2
  (в расширенном поиске 4) самых близких по смыслу фрагмента, которых в ней
  нет. Порядок и состав лексической выдачи не меняются, связанные документы
  подтягиваются по прежним правилам.
- Любая ошибка индексации или запроса эмбеддинга (HTTP, формат, NaN, таймаут)
  оставляет только BM25 и записывает код в журнал; это не считается отсутствием
  сведений в базе.
- Векторы — `array('f')` (4 байта на число), только стандартная библиотека.

## Веб-чат

`web/app.py` строит индекс эмбеддингов в фоновом потоке после старта, если
задан `EMB_MODEL` (через `compose.yaml` и `.env`; бюджет `PSB_DENSE_SECONDS`,
по умолчанию 600 с). Пока индекс строится или если провайдер вернул ошибку,
чат работает на BM25. Состояние видно в `/healthz` → `dense`: `off`,
`indexing`, `dense_enabled` или `dense_disabled:<код>`. Регрессии —
`web/tests/test_app.py`, класс `DenseIndexTests`.

## Проверка

Локальный стенд повторяет прокси платформы: `/chat/completions` → DeepSeek
(`deepseek-flash`, `low`), `/embeddings` → BAAI/bge-m3 (официальный ONNX, CPU).

**Поиск** (`evaluation/dense_retrieval_audit.py`, база организаторов; доля
найденных эталонных положений `eval/cases.json` и 64 перефразировок из
`evaluation/make_paraphrases.py`):

| Набор | BM25 | BM25 + bge-m3 |
|---|---:|---:|
| Исходные вопросы, 32 | 32/32 | 32/32 |
| Перефразировки, обычный поиск | 59/64 | 61/64 |
| Перефразировки, расширенный поиск | 60/64 | 64/64 |
| Медиана контекста, символов | 7 627 | 7 862 |

**Ответы** (`evaluation.run_corpus`, корпус `demo-paraphrase`: 34
перефразировки демо-вопросов с элементным эталоном демо):

| | BM25 | BM25 + bge-m3 |
|---|---:|---:|
| Демо, 18 | 18/18 | 18/18 |
| Перефразировки, автоматически | 31/34 | 32/34 |
| Перефразировки, верно по ручной сверке | 30/34 | 33/34 |
| Ложные отказы из-за поиска | 3 (12-p2, 13-p1, 13-p2) | 0 |

Ручная сверка расходится с автоматической в двух местах:
`16-p1` (гибрид) верен — «стоимость упаковки и доставки уже входит в цену»,
а эталон ждёт слово «включ»; `2-p2` (BM25) неверен — ответ «три месяца» для
«руководителя финансового учёта», а эталон засчитал «шести месяцев» внутри
процитированной нормы. На `2-p2` гибрид дал общий отказ `unverified`.

## Реранкер (только по флагу `PSB_RERANK=1`)

`psb_llm.RerankClient`, `Retriever.enable_rerank`, `_rerank_candidates`;
включение — `solution.enable_optional_rerank`. Регрессии —
[tests/test_rerank.py](../tests/test_rerank.py).

- Формат прокси платформы: `POST {LLM_BASE_URL}/rerank` с
  `{model, query, documents, top_n}` → `results[{index, relevance_score}]`;
  модель — `RERANKER_MODEL`, ключ — `RERANKER_API_KEY` или ключ генерации.
- Реранкер читает следующие 30 лексических кандидатов, которых нет в выдаче,
  и добавляет 2 (в расширенном поиске 4) лучших. Выдачу BM25 он не
  переставляет и не сокращает; при любой ошибке (HTTP, формат, индекс вне
  списка, таймаут) до конца запуска остаётся поиск без него (`rerank_failed`).
- Регламент задаёт на платформе `RERANKER_MODEL` (Qwen3 Reranker 8B), но
  одного этого недостаточно: реранкер включается, только если ещё задан
  `PSB_RERANK=1` (иначе в журнале `rerank_off`). Причина — замер ниже: прирост
  в пределах одного вопроса, а задержка 8B на прокси неизвестна и
  добавляется к каждому поиску при лимите 20 минут.

Замер поиска (`evaluation/retrieval_bench.py`, локальный Qwen3-Reranker-0.6B,
ONNX int8, CPU; без эмбеддингов; контекстные заголовки фрагментов включены):

| Набор | без реранкера | с реранкером |
|---|---:|---:|
| Исходные вопросы, 32 | 32/32 | 32/32 |
| Перефразировки, обычный / расширенный поиск | 60/64 / 60/64 | 60/64 / 60/64 |
| LegalBench-RU, обычный / расширенный | 136/139 / 137/139 | 137/139 / 137/139 |
| Медиана контекста LegalBench, обычный / расширенный, символов | 2 812 / 5 673 | 3 642 / 7 555 |

Отчёты: `evaluation/reports/rb-ctx*`, `rb-rerank*`. Измерена малая модель
0.6B, а не 8B платформы; ответы с реранкером не прогонялись. Перефразировки,
которые не находит лексика, находят эмбеддинги (таблица выше), а не реранкер:
его кандидаты берутся из той же лексической выдачи.

## Границы

- Индексация 1 113 фрагментов на CPU стенда заняла 291 с; скорость прокси
  платформы неизвестна. Если она ниже, гибрид отключится по прогнозу.
- Перефразировки получены из набора настройки и написаны моделью решения —
  это измерение разработки, не независимый контроль.
- Один прогон на вариант.
