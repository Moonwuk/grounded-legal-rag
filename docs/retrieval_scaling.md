# Навигация по юридической базе и масштабирование

Дата исследования: 10 ноября 2026. Это сравнение подходов и план развития, а не утверждение, что перечисленные системы уже внедрены или испытаны на нашем корпусе.

## Решение для проекта

Рекомендуется сочетать каталог документов, поиск точных терминов и идентификаторов, семантический поиск и восстановление связанного контекста. Основанием ответа всегда остаётся оригинальный текст. Оглавление, метаданные, граф и резюме помогают найти источник, но не заменяют его.

Для текущего ZIP сохраняется автономный поиск стандартной библиотекой Python. Для растущего сервиса предлагается интерфейс сменных поисковых движков: первоначально BM25, затем гибридный движок с фильтрами. Qdrant — первый кандидат для отдельного сравнения; Elasticsearch — альтернатива, особенно при уже существующем поисковом кластере. Установка обоих одновременно без измерений не нужна.

## Что измерено сейчас

Корпус: 21 документ, 1 106 фрагментов. Поиск занимает около 15 мс на вопрос в текущем окружении. Основное наблюдаемое время запроса приходится на API генерации и проверки. Денежную стоимость запросов по биллингу провайдера не измеряли.

| Настройка | Медианный контекст, символы | Максимальный контекст | Покрытие размеченных оснований |
|---|---:|---:|---:|
| TOP_K=12 | 12 310 | 27 245 | 32/32 случая |
| TOP_K=6 | 6 694 | 14 027 | 32/32 случая |

Медианный объём исходного текста уменьшился примерно на 46%. Это не означает такое же снижение стоимости всего запроса: есть системные инструкции, JSON, выходные токены и повторные проверки. В API-представлении фрагмента также убраны повторяющийся заголовок и технические смещения; они сохранены внутри приложения. Измерения выполнялись на наборе разработки: 37 сценариев, из них 32 с положительной разметкой. Набор использовался при настройке; независимость и обобщение не доказаны. TOP_K=4 уже терял основание многодокументного запроса и не выбран.

## Сравнение подходов по первоисточникам

| Подход | Что даёт | Решение для нашего случая |
|---|---|---|
| Qdrant hybrid search и payload indexes | Сочетание семантического и точного поиска; индексированные фильтры по метаданным | Первый кандидат для серверного поиска при росте. Сравнить качество, RAM, время индексации и эксплуатационные расходы с baseline. [1–2] |
| Elasticsearch hybrid + RRF | Объединение полнотекстового и векторного ранжирования | Сильная альтернатива при потребности в полноценном поисковом сервисе. Учесть текущую лицензию, доступность нужных возможностей и нагрузку перед выбором. [3] |
| LlamaIndex AutoMergingRetriever | Возврат от нескольких найденных дочерних фрагментов к их родительскому контексту | Подход хорошо соответствует структуре «статья — пункт — исключение». Можно реализовать принцип без зависимости от всего фреймворка. [4] |
| PageIndex | Дерево документа и навигация по нему с участием LLM | Полезен для длинных структурированных документов. Сравнивать как дополнительный маршрут; нельзя считать бесплатным или автоматически быстрым. В README масштабирование через File System относится к облачному варианту. [5] |
| RAPTOR | Иерархия кластеров и генерируемых резюме | Кандидат для обзорных вопросов по длинным коллекциям. Резюме использовать только для маршрутизации; цитировать исходные фрагменты. [6] |
| Microsoft GraphRAG | Локальный поиск по сущностям и глобальные обзоры коллекции | Рассматривать для вопросов по связям и обзоров. Global Search ресурсозатратен по документации; для обычного срока оплаты полный графовый конвейер не обоснован. [7] |

Это подбор подходящих вариантов, не универсальный рейтинг. Рекламные проценты PageIndex и результаты RAPTOR на других задачах не являются прогнозом для ПСБ. Бенчмарки финансовых документов не заменяют тесты русскоязычных договоров, редакций и исключений.

## Предлагаемый маршрут запроса

1. Получить разрешённую область данных из доверенного контекста приложения. Права доступа нельзя брать из текста вопроса или документа.
2. Найти договор, контрагента, статью или тему через каталог и точный индекс. При неоднозначности сохранить несколько кандидатов или запросить уточнение.
3. Объединить лексические и семантические кандидаты через RRF. Семантическую ветку добавлять после проверки её выигрыша на отложенных вопросах; не считать BM25-оценку вероятностью правильности.
4. При необходимости переранжировать небольшой набор кандидатов, а не весь корпус. Лимит определяется измерениями; дополнительный реранкер не обязан улучшать стоимость каждого запроса.
5. Восстановить родительскую статью/раздел, исключения, определения и связанные изменения. Ограничение размера не должно отрезать условие применимости.
6. Сформировать компактный пакет оригинальных доказательств и выполнить генерацию с проверкой.

Векторная близость не определяет юридическую силу. Новейший документ не всегда применим к старому событию. При неизвестной дате или неразобранном условии нельзя жёстко исключать возможную редакцию.

## Каталог и связи

Предлагаемые поля: `document_id`, `version_id`, `content_hash`, `document_type`, `title`, `contract_id`, `counterparty_ids`, `article_path`, `parent_id`, `source_offsets`, `source_format`, `ingested_at`, `valid_from`, `valid_to`, `applicability_condition`, `access_scope`.

Метаданные реквизитов извлекаются из загруженного корпуса; известные компании и номера договоров нельзя зашивать как единственный способ навигации. Каждое утверждение о действии редакции должно иметь ссылку на исходный фрагмент. Неопределённость хранится явно, а не заменяется догадкой.

Дата подписания, начало действия и условие применимости — разные поля. Например, «спецификации, подписанные после определённой даты» не заменяется фильтром по дате поставки. Дата выгрузки не считается датой вступления нормы в силу.

Для первого этапа достаточно таблицы связей `amends`, `supersedes`, `refers_to`, `exception_to`, `defines`. Связь должна иметь основание в документе. Не требуется сразу строить LLM-граф всего корпуса. Текущий прототип сохраняет соседние фрагменты и некоторые связанные документы эвристиками; полноценного каталога и движка применимости пока нет.

## Обновление и рост

- Хранить оригиналы неизменными. Разделять исходный текст для цитирования и нормализованное поисковое представление. Не заменять похожие символы в оригинале: для юридического идентификатора это может изменить смысл.
- Обновлять индекс по хешу содержимого и версии парсера/модели эмбеддингов. Не пересчитывать неизменившиеся документы.
- Собирать новую версию индекса отдельно и атомарно переключать активный снимок. Один ответ должен использовать согласованный снимок базы.
- При удалении или изменении документа инвалидировать его фрагменты, связанные резюме, графовые рёбра и кэши. Проверять, что старый источник не продолжает появляться в выдаче.
- В ключ кэша включать версию корпуса, параметры поиска и область доступа. Не переносить ответы между конкурсными ID; общий неизменяемый индекс допустим, состояние диалога — нет.
- Для сервиса предусмотреть дисковый индекс и фоновые обновления. Текущий загрузчик имеет защитные лимиты 64 МиБ по сумме файлов и 8 МиБ на файл: это ограничение прототипа, не заявление о поддержке больших коллекций.
- Измерять рост на разных размерах и структуре корпуса, а не только копировать одинаковые документы. Отдельно считать время холодного старта, RAM, p50/p95 поиска, индексацию и время обновления.
- Переходить к шардам/распределённому кластеру по измеренному SLA, памяти и изоляции нагрузки, а не по произвольному числу документов.

Для конкурсного запуска действуют отдельные ограничения: доступные библиотеки, 8 CPU, 16 ГБ RAM, 20 минут и передаваемая платформой база. Внешняя поисковая БД или дополнительный облачный API в ZIP не предполагаются доступными. Переносимый индекс должен соответствовать хешу предоставленного корпуса; при несовпадении нужен пересчёт.

## Приёмка следующего этапа

Создать отложенный набор, который не участвует в выборе параметров. Включить новые названия компаний и номера договоров, похожих контрагентов, границы дат, изменения отдельных пунктов, отсутствие исторической редакции, документы без ответа, косвенные инъекции, многодокументные и диалоговые вопросы.

Сравнить BM25, BM25 с каталогом/родительскими разделами, гибридный поиск, гибридный поиск с реранкером, затем отдельные tree/graph-маршруты. Использовать одинаковые корпус, вопросы, генератор и проверку. Измерять полноту найденных оснований, правильность редакции, необоснованные отказы, точность цитат, поддержанность всех выводов, итоговые токены, вызовы и задержку. Побеждает измеренное сочетание качества и затрат; выбор технологии пока предварительный.
