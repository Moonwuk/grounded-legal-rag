## Почему нельзя переносить старый answer benchmark без адаптации

> Все три несовместимости ниже исправлены в `evaluation/` с регрессиями, падающими на прежнем коде; см. [статус интеграции стенда](../evaluation/PR_STATUS.md). Ниже — исходная диагностика.

**1. Обёртка меняет поведение нового runtime.** TracedRetriever предоставляет search/evidence, но не documents/reference_gaps/complete_sources. Это выключает новые пути учёта документов и структурных зависимостей. [Воспроизведение на одобряющей заглушке](../results/external_evaluation_wrapper_compatibility.json): при реально имеющемся сервисном паспорте прямой Retriever выдаёт answer19месяцев, старая обёртка превращает его в partial с требованием предоставить уже имеющийся документ. Это дефект наблюдения, не ошибка production-поиска. Нужна прозрачная передача интерфейса и проверка одинакового результата напрямую/через обёртку.

**2. Валидатор не проверяет новый связный answer.** Он разбирает candidate.claims и сравнивает равенство rendered_answer/answer, но не проверяет смысл самого видимого prose. [Негативная калибровка](../results/external_evaluation_false_acceptance.json): настоящие claims о45днях сохранены, а candidate.answer, rendered_answer и answer заменены на «Оплачивать товар вообще не требуется.» — старый валидатор всё равно возвращает PASS без ошибок. Это искусственная подмена входа оценщика, не наблюдавшийся ответ реальной модели и не обход runtime. Неизвестный смысл видимого ответа должен как минимум получать NOT_EVALUATED, а доказанно неверный —FAIL; настоящая цитата не должна делать ложный prose успешным.

**3. Адреса восстановленных фрагментов.** Worker собирает цитируемые fragments из исходного списка frags, хотя текущий search создаёт восстановленные блоки с другими диапазонами/ID. Источники нужно брать из фактически принятого evidence; иначе возможны ложные citation failures. Этот пункт установлен по коду, отдельный частотный замер не выполнялся.

Собственные [37unit-тестов стенда](../results/external_evaluation_validator_tests.txt) на копии нынешнего runtime проходят; они не покрывают указанные несовместимости. Использовались локальные HTTP-заглушки, не DeepSeek. Поэтому зелёные unit-тесты и прежняя калибровка0/7не делают текущий answer-score надёжным.

Собственный replay дополнительно проверен [тремя регрессиями](../results/external_evaluation_replay_tests.txt): неверный документ/текст/разорванный span не дают успех, частичный набор отличается от полного допустимого, отсутствие обязательных оснований не превращается в100%. Эти тесты не исправляют старый answer-валидатор — они проверяют только новый поисковый replay.

## Что использовать дальше

Полезны formal specs, отдельные корпуса/gold, воспроизводимые source spans, метаморфные преобразования, конечные бюджеты и раздельные технические/содержательные метрики. Сохранённый набор уже пригоден для retrieval/stress-проверок. Полный answer benchmark требует адаптации интерфейса наблюдения, проверки именно опубликованного текста и отрицательной калибровки нового формата, затем небольшого реального smoke. Стенд пока не подключён к рабочему индексу и не включён в сабмит.

Повтор после выборочной распаковки полученного пакета:

```bash
python3 eval/replay_external_retrieval.py --evaluation-root /path/to/evaluation --corpus synthetic --source-commit 3985d8d3ca13762c339f2ac1e8ae92cc3f5985d1 --out results/my-replay.json
```

Полные500кейсов и исходные журналы не пересоздавались генератором. Архивы и gold используются в точности из полученного пакета; это не независимо проверенная правовая разметка. Названия holdout сохранены из пакета, а не обещают слепой контроль будущих изменений после знакомства с набором.
