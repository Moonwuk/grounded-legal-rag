# Остановка ответа и очередь вопросов

При настроенной [серверной истории](chat_history.md) отправка вопроса добавляет его
в очередь текущего диалога. Пока готовится ответ, можно отправить следующие вопросы.
Они выполняются последовательно и получают контекст уже завершённых ответов.
Под полем диалога видны текущая обработка, ожидающие вопросы и кнопки управления.

- «Остановить» завершает текущую серверную генерацию и ставит очередь на паузу.
  В истории остаются вопрос и статус «Ответ остановлен»; этот обмен не входит в
  контекст следующих запросов.
- «Убрать» удаляет ожидающий вопрос из очереди. Если вопрос успел начать обработку,
  он останавливается, а оставшаяся очередь ставится на паузу.
- «Продолжить» запускает оставшиеся вопросы после остановки или технической ошибки.
- «Повторить» после ошибки ставит повтор перед зависимыми ожидающими вопросами,
  возобновляет очередь и заменяет последнюю неудачную попытку.

Очередь хранится в SQLite, доступна с другого устройства и продолжает работать
после закрытия браузера. Новый диалог и переключение истории не отменяют работу
другого диалога. Черновик в поле ввода не стирается при получении ответа.
Кнопка «Новый диалог» находится сверху в панели истории; на телефоне — внутри меню.
При выбранной папке она создаёт диалог в этой папке.

## Реализация и ограничения

`web/queue.py` обслуживает `chat_queue` и `chat_jobs`. Worker захватывает вопрос
атомарно; одновременно работает не более одного вопроса одного диалога и не более
`WEB_WORKERS` вопросов на процесс веб-сервера (по умолчанию 2). Этот лимит общий с
совместимым синхронным `/api/chat`. Обход активной очереди через старый маршрут запрещён.

`web/generation.py` запускает отдельный процесс через spawn для каждого ответа.
Он использует тот же корпус, Retriever и проверяемую политику ответа. Готовые
векторы основного индекса передаются вместе с корпусом, если плотный поиск включён.
Остановка передаётся по приватному каналу дочернему процессу, который завершает
себя, закрывая в том числе соединение с API модели. Подтверждение остановки
появляется после завершения обработчика. Приложение не может гарантировать отмену
работы/начислений на стороне внешнего провайдера после получения им запроса.

Worker обновляет аренду задания раз в секунду; после 15 секунд без продления
задание считается прерванным. Такие вопросы не повторяются автоматически: ошибка
попадает в историю, очередь ставится на паузу. При штатной остановке сервера
выполняемые ответы останавливаются, ожидающие сохраняются. При перезапуске
очереди без прерванного активного задания продолжаются. На ответ отведено до
150 секунд внутри политики и до 180 секунд вместе с запуском процесса.

До пяти ожидающих вопросов на диалог, максимум 20 попыток в истории с учётом
зарезервированных мест очереди, до 100 заданий за жизнь диалога (включая убранные).
Вопрос — до 10 000 символов, контекст — до 30 000. При технической ошибке зависимые
вопросы не запускаются автоматически. Перемещение в корзину запрещено, пока есть
выполняемые или ожидающие вопросы: сначала остановите ответ и уберите очередь.

В текущей конфигурации используется один процесс uvicorn. Если оператор запускает
несколько процессов веб-сервера, SQLite предотвращает параллельную работу одного
диалога, но общий лимит процессов модели равен WEB_WORKERS × число процессов uvicorn.

## API

Все маршруты требуют проверенного логина прокси и используют private/no-store.

| Метод | Действие |
|---|---|
| `POST /api/chats/{id}/jobs` | Добавить вопрос: JSON `id` (UUID), `question`; 202 |
| `GET /api/chats/{id}/jobs` | Согласованный снимок истории, ожидающих/активного заданий и паузы |
| `DELETE /api/chats/{id}/jobs/{job_id}` | Убрать ожидающий вопрос или остановить активный |
| `POST /api/chats/{id}/jobs/resume` | Возобновить очередь; Content-Type application/json |

Повтор POST с тем же ID и вопросом не создаёт второй запрос — это защищает от
потерянного HTTP-ответа. Один ID с другим содержимым возвращает 409. В браузере
снимок обновляется примерно раз в 700 мс при работе и раз в 2,5 секунды без заданий.
Данные очереди не передаются между пользователями или диалогами.
Без серверной истории остаётся прежний синхронный режим без сохраняемой очереди.

## Проверки

`web/tests/test_queue.py`: FIFO, контекст, идемпотентность, остановка и пауза,
удаление ожидающего вопроса, восстановление после сбоя worker, лимиты и права,
совместимость с корзиной, повтор до зависимых вопросов, параллельные диалоги.
Два теста используют реальный дочерний процесс и локальный HTTP API: остановка
медленного запроса и полный проверенный ответ с точными цитатами.

`web/browser-tests/queue.cjs` запускается только с локальной фикстурой
`web/browser-tests/queue_fixture.py`: отправка во время ответа, перезагрузка,
остановка, пауза, удаление ожидающего, другое устройство, продолжение, сохранение
черновика, источники и новое положение кнопки диалога. Фикстура заменяет только
генерацию, хранение и очередь настоящие. В рабочий Docker-образ она не входит.
