## 3. Находки подробно

### 3.1 Контроль достоверности

#### Д1. Выдуманное число проходит как «расчёт» (Высокая; только #22)

**Где.** `prototype/psb_policy.py` в #22: `_same` (строки 1038–1043),
`_derivable` (1046–1072), `calculation_shown` (1075–1116), `prose_grounded`
(1119–1134). В `main` функции `calculation_shown` нет: `prose_grounded`
(`main`, 555–567) такое число отклоняет.

**Как устроено.** Если в тексте модели есть число, которого нет в основании,
`prose_grounded` даёт второй шанс через `calculation_shown` (строка 1134). Новое
число принимается, если выполнены два условия:

1. Оно стоит в «предложении с расчётом». Признак такого предложения:
   регулярное выражение `[×*+=÷/]|\s[−–-]\s` (строка 1104).
2. Оно получается одной или двумя арифметическими операциями из чисел ответа,
   которые есть в основании, с допуском округления (`_same`). Для целого числа
   допуск меньше 0,5.

**Почему это дыра.**

- Символ `/` есть в каждом номере договора: «А-08/2024», «П-17/2024»,
  «ПТ-05/2023». Промпт сам требует называть документ, и его образец построен
  так же: «По договору подряда № Д-3/2030 с ООО «Вектор» аванс составляет 20%
  цены» (`SYSTEM`, строка 151 в #22). Поэтому почти любое предложение с номером
  договора считается «расчётом».
- В операнды попадают номер договора (8, 17, 5), год (2024) и номера пунктов:
  «3.1» и «3.2» разбираются как десятичные числа 3,1 и 3,2 (`_CALC_NUMBER`,
  строка 1031). С допуском 0,5 из них за две операции получается почти любое
  небольшое целое число.

**Сценарий (по коду, прослежен вручную).** Вопрос 1 демо. Модель ошибается и
пишет: «По договору № А-08/2024 арендная плата — 450 000 рублей в месяц,
вносится не позднее 10-го числа (п. 3.1, 3.2).» В договоре: не позднее 5-го
числа (п. 3.2).

- Числа 10 нет ни в п. 3.1–3.2, ни в шапке договора, ни в имени файла, ни в
  вопросе. Первая проверка (строка 1131) не проходит, вызывается
  `calculation_shown`.
- Текст делится по `(?<=[.!?;])\s+` (строка 1103). Первое «предложение»
  заканчивается на «(п.» и содержит `/`, поэтому все его числа, включая 10,
  считаются показанными в расчёте.
- Операнды ответа, которые есть в основании: 8, 2024, 450 000, 3,1, 3,2.
  3,1 × 3,2 = 9,92, и `_same(9.92, 10)` возвращает True, потому что
  |9,92 − 10| < 0,5.
- `prose_grounded` возвращает True. В положениях 3.1–3.2 нет слов из
  `_SOURCE_ONLY`, поэтому барьер ограничений не включается. В batch проверяющего
  вызова по умолчанию нет (`solution.py:208` в #22), ответ выходит со статусом
  `answer` (ветка `if not verify`, строки 1807–1845). Для судьи это выдуманный
  факт и 0 за вопрос.

В #22 есть `tests/test_calculations.py`, но отрицательного примера с номером
договора в нём нет (судя по названиям тестов).

**Что сделать.**

- Считать расчётом только явную запись `a op b = c` (или `a op b op c = d`),
  где операнды и результат стоят вокруг знаков. Признак «в предложении есть
  знак» не годится.
- Перед поиском расчёта убирать из текста номера документов
  (`[А-ЯA-Z]{1,8}-\d+/\d{4}`), даты, номера пунктов и статей. Для ссылок уже
  есть `_REFERENCE` (строка 827).
- Убрать допуск округления для целых: требовать точного равенства, допуск
  оставить только для записанных десятичных знаков.
- Добавить отрицательные тесты из раздела 6.

#### Д2. Числовая граница не считается ограничением, неверное «Да» проходит (Высокая; оба, в `main` прикрыто проверяющим)

**Где.**

- #22, `prototype/psb_policy.py`: `_SOURCE_ONLY` (331–333), `_RESTRICTIONS`
  (338–344), `_UPPER_BOUND_SOURCE` (379–380), `grounding_basis` (1011–1026;
  реплики пользователя добавляются в строке 1013), расчёт `restricted` в
  `answer_steps` (1770).
- `main`: `_SOURCE_ONLY` (245–247), `_RESTRICTIONS` (252–258), `grounding_basis`
  (537–552), `restricted` (888). Дыра та же, но текст затем обязательно
  проходит проверяющий вызов (строки 905–909).

**Как устроено.** Барьер ограничений срабатывает на «не вправе», «не может»,
«только», «лишь», «при наличии / условии», «по соглашению», «за исключением»,
«запрещ…». Верхнюю границу #22 распознаёт только в форме «не может / не должен
превышать» или «не может быть более / больше / дольше / свыше». Формы «не более
N», «не позднее N», «не свыше N», «до N» ограничением не считаются.
Регулярное выражение `_BOUND` (строка 720) такие формы знает, но используется
только в `_restates_bound`, чтобы оправдать слово «только» в ответе. Числа из
вопроса пользователя считаются обоснованными.

**Сценарий (по коду).** Вопрос 11 демо: «Хочу взять оригинал договора из
архива на четыре рабочих дня. Это разрешено?» В служебной записке: «по заявке
в СЭД на срок не более 3 (трёх) рабочих дней». Модель отвечает неверно: «Да,
оригиналы выдаются по заявке в СЭД, можно взять на четыре рабочих дня».

- В тексте записки нет ни одного слова из `_SOURCE_ONLY`, поэтому
  `restricted` = False и `restrictions_kept` не вызывается.
- «Четыре» = 4 есть в вопросе, проверка чисел пройдена.
- Барьеры `prose_scope_safe` и `added_assertions_safe` не срабатывают: в тексте
  нет исключающих слов, отрицания роли и утверждений о содержании документа.
- В batch #22 ответ публикуется как `answer`.

В сохранённом живом прогоне `main` модель ответила правильно («Нет. … на срок
не более 3 рабочих дней», `results/warn_release_live_20261110T171436Z/submission.csv`,
id 11). Программной страховки на случай ошибки модели нет.

Это общий класс: «можно ли X, если источник ограничивает X числом». Таких
вопросов в юридическом наборе много: сроки, суммы, количества.

**Что сделать.**

- Добавить класс «числовая граница»: «не более | не свыше | не позднее |
  не менее | не ранее | до» + число + единица. Если он есть в выбранном
  положении, текст ответа обязан содержать число границы. По такому же
  принципу уже работает пара `_UPPER_BOUND_SOURCE` / `_UPPER_BOUND_ANSWER`.
- Если в вопросе есть число с той же единицей, сравнить его с границей кодом и
  проверить полярность ответа («Да» или «Нет»). Это детерминированно и дёшево.
- Числа, которые есть только в вопросе, допускать в тексте в двух случаях:
  в конструкции контраста («а не», «вместо», «превышает») или когда положение
  не содержит другого значения той же единицы, то есть число является
  условием сценария (например, сумма договора).

#### Д3. Независимость от отсылки в batch принимается со слов модели (Средняя; только #22)

**Где.** `answer_steps` в #22: `local_reference` (1795–1802), ветка
`if not verify:` (1807–1845), подтверждение проверяющим (1861–1865), текст
хвоста в `gap_lines` (1524–1531).

PR #23 разрешил полный ответ при отсутствующей отсылочной статье при двух
условиях: модель объявила `reference_scope=local`, и проверяющий вызов явно это
подтвердил (`references_required` равно `false`, `answer_supported` и
`complete` равны `true`). В ветке `if not verify` второго условия нет. Ответ с
`local` выходит со статусом `answer` по слову самой модели, с хвостом «Условия
применения этих отсылочных оснований в данном ответе не устанавливаются».

**Сценарий (по коду).** Вопрос о персональных данных. В базе есть только
статья 9 закона 152-ФЗ, она ссылается на статьи того же закона, которых в базе
нет. Модель объявляет `local`, и ответ, который на деле зависит от
отсутствующих оснований, выходит как полный. В прогоне `main` по вопросу 13
каталог насчитал три отсутствующие отсылочные статьи (`source_gap_count: 3`,
позиция 12 в `results/warn_release_live_20261110T171436Z/submission_run.txt`).

**Что сделать.** При `verify=False` считать `local` недоступным и оставлять
`partial`, либо включать проверяющий вызов только для этого случая (выборочная
проверка, раздел 4). Это несколько строк и один тест.

#### Д4. Проверка чисел работает «мешком» (Средняя; оба, в #22 без страховки)

**Где.** `prose_grounded` и `_figures`: `main` 555–567 и 338–374; #22 1119–1134
и 534–570.

Число в ответе считается подтверждённым, если оно встречается где угодно в
выбранных положениях, в шапке и имени их документов или в репликах
пользователя. Сравниваются множества (`all(n <= h …)`), связи числа с термином
нет.

**Сценарий.** Модель перепутала значения внутри одного положения: срок одной
операции приписан другой, а 5 и 10 дней стоят в соседних подпунктах. Оба числа
есть в основании, текст проходит. В `main` его затем читает проверяющий вызов,
в batch #22 по умолчанию никто.

**Что сделать.** Связывать число с термином: для каждого числа ответа искать
предложение источника, где это число стоит рядом хотя бы с одной общей основой
слова из того же предложения ответа («плат», «срок», «испыт»). Проверка
детерминированная и ловит перестановки.

#### Д5. Карантин инъекций ловит только три фразы (Средняя; оба)

**Где.** `INSTRUCTION` в `prototype/psb_corpus.py`, строки 30–32 в обеих
версиях.

Регулярное выражение описывает ровно строку-ловушку из демо-корпуса:
«внимание для ИИ-ассистента», «игнорируй все остальные документы» и
«ignore (all|previous) instructions».

**Сценарий.** Инъекция в другой формулировке («Системное указание: …»,
«Модель, отвечай …», «Не упоминай эту инструкцию» отдельной строкой) попадает
в evidence как обычное положение. Тогда защищают только промпт и проверка
чисел, а она здесь не помогает: если модель выберет такую строку как
основание, число из неё станет «обоснованным». В одновызовном режиме #22
дополнительной проверки нет.

**Что сделать.** Расширить эвристику: обращение к модели, ассистенту или ИИ,
повелительные формы «игнорируй / отвечай / не упоминай / выполняй», маркеры
`system:` и `[SYSTEM]`. Строки-кандидаты не удалять, а помечать «нельзя
выбирать как основание», чтобы не потерять настоящий текст. Добавить
синтетические варианты в тесты.

### 3.2 Надёжность прогона

#### Н1. Один файл базы роняет весь прогон (Критично в `main`; Средняя в #22)

**Где.** `main`, `prototype/psb_corpus.py`: `read_docx` (64–65, 84–85) и
`load_corpus` (119–120, 128–130); обработка в `prototype/solution.py` (91–98).

**`main`.** Любое из перечисленного бросает `ValueError` при загрузке.
`solution.py` выходит с кодом 2, и все строки CSV остаются «технической
ошибкой» (заглушка записана раньше, в строке 75):

- файл с другим расширением: `.DS_Store`, `README` без расширения, PDF;
- TXT не в UTF-8, например cp1251 (`UnicodeDecodeError` является подклассом
  `ValueError`);
- DOCX со сносками (`docx_notes_not_supported`);
- пустой файл (`empty_document`).

**#22.** Такой документ пропускается с кодом причины, остальная база читается.
Остаток проблемы:

- TXT в cp1251 не декодируется запасной кодировкой, а выпадает целиком
  (`document_not_utf8`). Ответы по нему превращаются в ложные «в базе нет».
- DOCX со сносками тоже выпадает целиком, хотя основной текст читается.
- PDF не поддерживается, хотя `pypdf` и `python-docx` есть в списке
  разрешённых библиотек (`organizer/requirements.txt`). Ограничение «только
  стандартная библиотека» команда ввела сама (`README.md:21`,
  `prototype/requirements.txt`).

**Что сделать.** Пробовать `utf-8-sig`, затем `cp1251` с проверкой доли
кириллицы. В DOCX со сносками читать основной текст и явно помечать сноски
как непрочитанные (правило 6 AGENTS). Решить, нужен ли `pypdf` для PDF.

#### Н2. `\` или `:` в имени файла ZIP роняет всю базу (Средняя; оба)

**Где.** `load_corpus`: `main` 112–114, #22 133–135. Код `unsafe_archive_path`
не входит в `DOCUMENT_ERRORS`, поэтому в #22 ошибка тоже фатальна.

**Сценарий.** Архив, в котором пути записаны с обратной косой чертой, или файл
с двоеточием в имени («Письмо от 15:04.txt»). Вся база не загружается, прогон
получает ноль. Свой стенд на это уже натыкался: «1 Windows failure на ZIP
backslash fixture» (`evaluation/FINAL_REPORT.md:21`). Утверждение черновика о
том, что такие пути пишет старый `Compress-Archive` из PowerShell 5.1, при
сверке не перепроверено: это внешний факт, в репозитории его нет.

**Что сделать.** Нормализовать `\` в `/` до проверки traversal. Двоеточие
отклонять только в позиции диска (`C:`). Небезопасный путь пропускать как
отдельный документ, а не валить всю базу.

#### Н3. Пустой вопрос или битая строка: CSV не создаётся вовсе (Средняя; оба)

**Где.** `prototype/solution.py`: `read_questions` (`main` 31–51, #22 32–52)
вызывается до первой записи `submission.csv` (`main`: вызов 72, запись 75;

**Сценарий.** Одна строка с пустым `question` (`main` 47–48), повтор `id`
(49–50), лишняя или недостающая колонка (42–43) или ошибка кавычек при
`strict=True` дают `ValueError` или `csv.Error`. Выход с кодом 2, файла нет.
Платформа сообщит «Отсутствует submission.csv»
(`organizer/technical_regulations_text.md:141`), весь прогон получит 0.

**Что сделать.** Невалидные строки не должны убивать валидные. Для пустого
вопроса записывать фиксированный ответ. При ошибке разбора CSV пробовать
нестрогий режим и писать CSV по тем ID, которые удалось прочитать.

#### Н4. `main` теряет проверенный запасной ответ (Средняя; `main`, исправлено в #22)

**В #22** `run_questions.advance` при любом исключении возвращает последнюю
отданную контрольную точку (`solution.py:120–125`).

#### Н5. `evidence_size_limit` роняет вопрос вместо обрезки (Средняя; оба)

**Где.** `Retriever.search`: `main` 310 и 314, #22 593 и 597.

Бюджет контекста «мягкий»: первая семья документов берётся всегда (`main` 271),
связанные документы добавляются уже после бюджета (`main` 278–287), а затем

**Сценарий.** База с длинными связанными документами. На своём стенде это

передавать признак неполноты (`partial`), а не бросать исключение.

#### Н6. Тайм-аут 45 с на нестримовый ответ (Средняя; оба, в #22 смягчено)

**Где.** `prototype/psb_llm.py`: `timeout=min(45., remaining)`, `main` 106,
#22 124. Поля `stream` в запросе нет.

Сервер молчит до конца генерации, поэтому сокетный тайм-аут срабатывает на
долгих ответах с рассуждением. Повтор отправляет тот же запрос с нуля.

**Свидетельство.** В журналах `main` четыре события `"kind": "timeout"`: три
подряд на одном вызове (все три попытки, по 51–53 с) в
`results/scope_baseline_clarify_20261110T145708Z/submission_run.txt` и одно в
`results/scope_live_20261110T143322Z/submission_run.txt`. В #22 уровень
рассуждений по умолчанию `low` (`DEFAULT_EFFORT`, `psb_llm.py:61`), риск ниже,
но не нулевой.

**Что сделать.** `stream: true` с тайм-аутом простоя около 30 с и общим
ограничением по дедлайну строки. Либо тайм-аут 90–120 с.

#### Н7. `MAX_TOKENS` без разумного нижнего предела (Низкая; оба, в #22 смягчено)

**Где.** `integer("MAX_TOKENS", 8192, 256, 65536)`: `main` `psb_llm.py:85`,
#22 `psb_llm.py:101`.

Нижняя граница 256. При значении платформы около 1024 рассуждения съедают весь
лимит. #22 это измерил и смягчил уровнем `low` и понижением уровня при обрезке
(`psb_llm.py:153–177`), но сам пишет, что при `MAX_TOKENS` около 1024 обрезка
на уровне `low` остаётся возможной (`docs/reasoning_budget.md:49`).

**Что сделать.** Брать `max(MAX_TOKENS, 4096)`, а при HTTP 400 повторять с
исходным значением.

#### Н8. `LLM_REASONING_EFFORT=medium` ломает каждый ответ (Низкая; оба)

**Где.** `main` `psb_llm.py:87–91`, #22 `psb_llm.py:103–105`.

Допустимы только `none`, `low`, `high`, `max` (и `default` в #22). Значение
`medium` даёт `ProviderError("invalid_reasoning_configuration")` на каждом
вызове. Проверка стоит в `complete`, а не в конструкторе, поэтому стартовая
проверка `ProxyClient(deadline)` в `solution.py` её не замечает: прогон не
падает сразу, а пишет техническую ошибку во все строки. Переменная выведена в
`.env.example` (строка 8) и `compose.yaml` (строка 17).

**Что сделать.** Проверять значение при старте. Неизвестное значение либо
передавать как есть, либо заменять на значение по умолчанию с записью в
журнал.

#### Н9. Битый JSON без повтора (Средняя; `main`, исправлено в #22)

**Где.** `main` `psb_llm.py:153–156` и 176–177: ошибка разбора сразу даёт
`invalid_model_response`. #22 `psb_llm.py:184–203`: один повтор с напоминанием
о формате (`format_retry`).

#### Н10. Плотный поиск хрупок и плохо масштабируется (Низкая / Средняя; только #22)

**Где.** #22, `prototype/psb_retrieval.py`: `enable_dense` (286–309),
`_dense_candidates` (335–354); запуск в `prototype/solution.py` (188–197).

- Один сбой эмбеддинга запроса ставит `_dense_failed = True` (строка 346) и
  отключает плотные кандидаты до конца прогона для всех вопросов.
- Сходство считается как `sum(map(operator.mul, …))` на чистом Python по всем
  векторам (352–353), под GIL. В демо-базе около 1 100 фрагментов (1 111
  непустых строк в `organizer/knowledge-base`), это быстро. Лимит кода —
  50 000 фрагментов (`MAX_FRAGMENTS`, `psb_corpus.py:14`); там полный перебор на
  каждый запрос станет заметным, а потоки будут мешать друг другу. Время при
  50 000 фрагментах не измерялось, это оценка. `numpy` и `faiss-cpu` есть в
  списке разрешённых библиотек.
- Индексация идёт последовательно, до первого ответа, и может занять до пятой
  части бюджета прогона.

**Что сделать.** Считать сбой запроса временным (счётчик подряд идущих сбоев
вместо флага навсегда). Для больших баз считать сходство через `numpy`.

**Сценарий.** Вопрос 8 демо: «“Альфа-Трейд” привёз мебель с дефектами…». Если

«Меридиан» есть во всех документах компании и ничего не различает. Извлечение
не пропускает строки карантина.

**Что сделать.** Брать только имя после организационно-правовой формы
(`ООО|АО|ПАО|ИП «…»`), исключать роли из «именуемое в дальнейшем «…»» и
пропускать строки карантина.

#### П2. Склонённые названия не распознаются (Средняя; оба)

**Где.** Сравнение по точной строке после `casefold` и замены пробелов на `-`:

**Сценарий.** «По договору с «Северным Складом»» (вопрос 7 демо), «у

букв) в окне из того же числа слов.

#### П3. Буст за номер пункта или статьи глобален (Средняя; оба, в #22 частично)

**Где.** `main` `psb_retrieval.py:185` (разбор номеров) и 200–201 (буст); #22
72–75 (`ARTICLE_REF`, `POINT_REF`, `POINT_OF_ARTICLE`), 430–435 и 450–451.

+25 получает любой фрагмент любого документа, который начинается с названного
номера. Выражение `(?:Статья\s+)?N(?:[.\s)]|$)` для «9» совпадает и с началом
«9.1».

**Сценарий.** «Что сказано в пункте 3.1?» поднимает пункты 3.1 всех договоров
и регламентов. «Статья 9» поднимает ещё и все пункты «9.x» всех договоров. При
`TOP_K=6` эти совпадения вытесняют нужные фрагменты.

#22 правильно связывает «пункт 4 статьи 114» (номер пункта в такой связке
больше не действует глобально) и резервирует место для названной статьи
(`_article_fragments`, 387–407, 493–498). Отдельные номера по-прежнему
действуют на всю базу.

**Добавлено при сверке (подтверждено в коде).** В `main` разбор номеров знает
только «пункт», «пункта», «пункте», «п.», «статья», «статьи» (строка 185).
Сокращение «ст.» и формы «статье», «статьёй», «пунктом» не распознаются: на
вопросе «по ст. 70 ТК» буст в `main` не срабатывает совсем. В #22 это
исправлено (`стать[а-яё]*|ст\.`, строка 72). Пример черновика со «ст. 9»
относится поэтому только к #22.

**Что сделать.** Применять буст только к документам, названным в вопросе
(номер договора, кодекс или закон, контрагент), а без такого указания давать

#### П4. Реплики ассистента не участвуют в поиске (Низкая / Средняя; оба)

#### П5. Морфология и полнота поиска (Средняя; оба, в #22 частично)

### 3.4 Ответ и форма

#### О1. Лексический барьер выбрасывал текст модели (Высокая; `main`, исправлено в #22)

**Где.** `main`, `psb_policy.py`: `_SOURCE_ONLY` (245–247), `restrictions_kept`
(261–269), расчёт `source_only` (888–889).

**Свидетельство.** В прогоне
`results/warn_release_live_20261110T171436Z/submission_run.txt` шесть событий
`policy_verdict` с `"prose": "source_only"` на позициях 1, 8, 12, 13, 16 и ещё
раз 16 (расширенная попытка). Это пять вопросов из 18: 2, 9, 13, 14, 17. Во
всех шести событиях `approved: true`. Пользователь получал набор цитат без
прямого ответа; например, ответ на вопрос 2 начинается сразу с цитаты статьи.

Поправка к черновику: там было «6 из 18 ответов». Событий шесть, вопросов
пять.

**Причина (по коду).** `restrictions_kept` требовал дословно повторить
оператор каждого класса из источника («не может», «по соглашению», «при
