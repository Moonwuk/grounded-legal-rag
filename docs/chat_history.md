# История чатов

По запросу владельца проекта диалоги хранятся на сервере и доступны с разных
устройств под одним логином. История содержит вопросы, ответы, статусы и карточки
источников. Кнопка «Новый диалог» оставляет прежний чат в списке; «В корзину» перемещает
его в корзину после подтверждения. Оттуда чат можно восстановить или удалить навсегда. Незавершённый диалог обновляется кнопкой «Обновить список».

## Настройка

1. Задайте случайный `CHAT_PROXY_TOKEN` в `.env` и передайте тот же секрет
   аутентифицирующему обратному прокси. Секрет не должен попадать в браузер или Git.
2. После успешной аутентификации прокси должен **перезаписывать** входные заголовки
   `X-Chat-User` проверенным логином и `X-Chat-Token` общим секретом.
   Для Caddy внутри `reverse_proxy`, после `basic_auth`:

   ```caddyfile
   header_up X-Chat-User {http.auth.user.id}
   header_up X-Chat-Token {env.CHAT_PROXY_TOKEN}
   header_up -Authorization
   ```

   Здесь переменная `CHAT_PROXY_TOKEN` должна существовать в окружении Caddy.
   Весь сайт закрывайте HTTPS и авторизацией. Прямой порт приложения оставляйте
   на `127.0.0.1`, как в `compose.yaml`.
3. Выполните `docker compose up --build -d --wait`. База SQLite находится в
   именованном томе `psb-web_chat-history`, `/history/chats.sqlite3` внутри контейнера.
   Она переживает пересоздание контейнера и обычный `docker compose down`.
   `docker compose down -v` удалит историю. Для резервного копирования используйте
   SQLite backup API или остановите контейнер перед копированием всего тома.

`CHAT_HISTORY_PATH` задаёт путь SQLite для запуска вне Compose; родительский каталог
должен существовать и быть доступен для записи пользователю приложения. При отсутствии
пути или токена серверная история выключена, интерфейс явно сообщает об этом и
использует прежний диалог в памяти вкладки. Ошибка доступа или сети не включает
молча временный режим.

## API и границы

Все операции истории проверяют секрет прокси и логин. Другой пользователь получает
404 для чужого ID, включая продолжение и удаление диалога.

| Метод | Действие |
|---|---|
| `GET /api/chats` | Чаты текущего пользователя, новые сверху |
| `POST /api/chats` | Создать диалог |
| `GET /api/chats/{id}` | Сообщения, полные ответы и источники |
| `DELETE /api/chats/{id}` | Переместить диалог в корзину |
| `POST /api/chat` | С `chat_id` и одним новым пользовательским сообщением продолжить сохранённый диалог |

Контекст для сохранённого чата сервер восстанавливает из собственной базы. История,
переданная клиентом вместо одного нового сообщения, отклоняется. Технические ошибки
видны в истории, но не передаются модели; повтор того же последнего неудачного вопроса
заменяет неудачную попытку. Ответ сохраняется сервером и при закрытии браузера.
Остановка контейнера во время генерации может прервать текущую попытку; уже сохранённые
ответы остаются. Существовавшие до обновления диалоги из памяти вкладки автоматически
не переносятся.

До 100 активных чатов и 100 чатов в корзине на логин, до 20 попыток вопроса на чат, прежний лимит контекста 30 000
символов. Одновременная генерация в одном чате и удаление во время неё возвращают 409.
Блокировка имеет срок 240 секунд для восстановления после аварии процесса.

У пользователей одного общего логина общая история. Для личных историй заведите
разные логины на прокси. База не шифруется приложением; доступ к тому и резервным
копиям должен быть ограничен оператором. Тексты сообщений не пишутся в диагностические
логи. Обычное удаление скрывает записи из приложения; гарантированное стирание из
резервных копий и файлов SQLite этой функцией не заявляется.

Проверки: `python -m unittest discover -s web/tests -v` и
`node --test web/tests/archive-scene.test.cjs` — изоляция, сохранность, источники,
контекст, повторы после ошибки, лимиты, конкуренция и восстановление интерфейса.


## Папки чатов

В истории доступны «Все чаты», «Без папки» и свои папки. «+ Папка» создаёт папку;
«Изменить папку» переименовывает или удаляет выбранную. «В папку» на карточке
диалога переносит его в выбранную папку или обратно в «Без папки». Один чат
принадлежит не более чем одной папке. Счётчики показывают число диалогов.
«+ Диалог в этой папке» начинает новый чат: при первой отправке сервер создаёт
его сразу в выбранной папке. При удалении папки все её чаты и сообщения сохраняются
в «Без папки». Операция не удаляет документы или подборки документов.

Папки и принадлежность хранятся в той же SQLite и изолированы по логину. Старые чаты
после обновления находятся в «Без папки»; их записи и сообщения не переписываются.
Новые таблицы `chat_folders` и `chat_folder_items` создаются при старте. Внешние ключи
удаляют только принадлежность при удалении папки/чата. Перенос не меняет историю,
время последнего ответа и блокировку генерации; возможен во время ответа.
На другом устройстве нажмите «Обновить список», чтобы получить изменения.

| Метод | Действие |
|---|---|
| `GET /api/chat-folders` | Папки текущего пользователя |
| `POST /api/chat-folders` | Создать папку, JSON `title` |
| `PUT /api/chat-folders/{id}` | Переименовать, JSON `title` |
| `DELETE /api/chat-folders/{id}` | Удалить папку, сохранив чаты |
| `PUT /api/chats/{id}/folder` | Перенести чат, JSON `folder_id` или null |
| `POST /api/chats?folder_id={id}` | Атомарно создать новый чат в своей папке |

Список и отдельный чат возвращают `folder_id` (null означает «Без папки»).
Лимит — 30 папок на логин; название 1–60 символов, без управляющих символов,
не должно совпадать с другой папкой этого пользователя без учёта регистра.
Редактирование/создание принимает JSON до 4 КиБ. Проверяется принадлежность
и чата, и папки; исчезнувшая папка возвращает 404 без потери текущей принадлежности.
Ответы API не кешируются. При одновременном переименовании/переносе применяется
последняя успешно завершившаяся операция.

`web/tests/test_chat_folders.py` проверяет изоляцию, сохранность истории, перенос,
удаление, лимиты, старую базу, создание в папке и завершение ответа во время переноса.
`web/browser-tests/folders.cjs` проверяет создание → перенос → переименование →
второе устройство → новый чат в папке → удаление без удаления чатов. Запуск аналогичен
[мобильному сценарию](mobile_ui.md). В отличие от полностью подменённого мобильного
сценария, он создаёт временную папку и пустые тестовые чаты на сервере, затем удаляет
только созданные им ID; ответы модели подменены, реальных вызовов LLM нет.


## Корзина

Раздел «Корзина» показывает удалённые чаты и дату удаления. В «Все чаты», «Без папки»
и пользовательские папки они не входят. «Восстановить» возвращает диалог с вопросами,
ответами, источниками, временем последнего ответа и принадлежностью к папке;
если папку удалили, диалог возвращается в «Без папки». После восстановления
интерфейс открывает диалог. Просмотр и продолжение доступны после восстановления.

«Удалить навсегда» доступно только для чата, который уже в корзине, и требует отдельного
подтверждения. Автоматической очистки и срока хранения нет. Лимиты — 100 активных
и 100 удалённых чатов на логин: при переполнении операция отклоняется, старые чаты
не вытесняются. Восстановление при заполненном активном списке также отклоняется.
Ранее удалённые до появления корзины записи восстановить этой функцией нельзя.

| Метод | Действие |
|---|---|
| `GET /api/chats?trash=true` | Корзина пользователя, новые удаления сверху, поле `deleted_at` |
| `DELETE /api/chats/{id}` | Переместить в корзину |
| `POST /api/chats/{id}/restore` | Восстановить; требуется Content-Type application/json |
| `DELETE /api/chats/{id}/permanent` | Окончательно удалить только из корзины |

Таблица `chat_trash` хранит время удаления и ссылку на чат. Исходная история не
переписывается при обновлении базы. Все операции проверяют владельца; чужие ID
недоступны. Удаление во время генерации запрещено, а запоздалое завершение после
истечения блокировки не меняет содержимое корзины. GET отдельного удалённого чата,
продолжение через модель и перенос по папкам возвращают 404 до восстановления.
Окончательное удаление активного чата возвращает 409. Физическое стирание данных
из резервных копий и свободных страниц SQLite не заявляется.

Проверки: `web/tests/test_chat_trash.py`, frontend-набор и
`web/browser-tests/trash.cjs`. Браузерный сценарий создаёт только свои временные
папку и пустой чат, проверяет корзину, второе устройство, восстановление в папку,
отмену окончательного удаления и окончательное удаление; в finally удаляет только
созданные им ID. Реальную модель не вызывает. Вопросы, ответы и цитаты при
восстановлении проверяются серверными и frontend-тестами.
