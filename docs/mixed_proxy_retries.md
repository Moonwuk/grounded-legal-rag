# Повторы после смешанных сбоев

14 ноября 2026. База: c0a0613ededa85babcc3fe7eec13b6bf25ec8d82,
ветка claude/magical-hawking-dkdi83. Шесть файлов prototype этой базы
побайтно совпали с предоставленным архивом №25
(SHA-256 c4fbd95664d7e15fcbaf5778eec6a19a1928e8fd9c9e7e10b8810e1bfaadc8c3).

## 1. Доступная попытка не использовалась

Последовательность HTTP 503 → HTTP 503 → finish_reason=length завершала вызов
ошибкой truncated_model_output. Хотя транспорт допускал четыре запроса,
условие attempt < 2 запрещало восстановление на третьем запросе.
Та же граница осталась у повтора неверного JSON и у удаления неподдерживаемого
reasoning_effort после HTTP 400/422.

Число транспортных запросов и доступность следующего теперь определяются одной
последовательностью TRANSPORT_BACKOFF_SECONDS. Все три механизма восстановления
проверяют retry_available. Повтор после обрезки и повтор формата по-прежнему
допускаются по одному разу. Общий максимум — четыре запроса на вызов;
пятый не появляется даже после смешанных ошибок. Бюджет логических вызовов
вопроса и очередь вопросов не менялись.

Планировщик №25 мог позднее перезапустить технически неудавшийся вопрос.
Поэтому дефект означал потерю локальной возможности восстановления и времени,
но не гарантированную окончательную заглушку каждого такого вопроса.

## 2. Повтор игнорировал паузу другого потока

Общий cooldown проверялся только перед первым запросом. Если другой поток
установил паузу 30 секунд, а текущий получил HTTP 503 и ждал свои 2 секунды,
его следующий запрос отправлялся уже на второй секунде.

Теперь пауза проверяется перед каждым запросом и повторно после ожидания:
другой поток мог продлить её, пока текущий спал. Если ожидание не помещается
в дедлайн, вызов завершается с run_deadline без нового HTTP-запроса.
Новые тела ответов, ключи и скрытые рассуждения в логи не добавлены.

## Проверки

[tests/test_mixed_proxy_retries.py](../tests/test_mixed_proxy_retries.py)
использует локальные ответы провайдера и управляемые часы:

- два 503, затем обрезка / неверный JSON / неподдерживаемый параметр и успех;
- все перестановки 503, обрезки и неверного JSON перед успешным четвёртым запросом;
- повторная ошибка того же типа не получает бесконечных попыток;
- последняя ошибка не создаёт пятый запрос;
- пауза другого потока действует и на повтор; продление во время ожидания учитывается;
- общий дедлайн ограничивает ожидание и задержки.

На исходном №25 набор обнаружил 3 проваленные проверки и 8 ошибок в подслучаях.
После исправления все 10 тестовых методов проходят. Эти числа описывают
проверку транспорта, а не качество юридических ответов.

В существующем HTTP-тесте test_recovery_and_transient_retry_bound
имитация sleep теперь продвигает часы, по которым считается cooldown:
раньше время в тесте не менялось после имитированного ожидания.
Проверки четырёх запросов и пауз 2, 5, 10 секунд сохранены.

Полный обязательный набор и проверка собранного ZIP:

    python3 -m unittest discover -s tests -v
    python3 build_submission.py
    python3 .github/scripts/check_submission.py

## Что не установлено

- MAX_TOKENS=1024 — воспроизведённая локальная конфигурация, не подтверждённое
  по логам значение окружения платформы.
- Причина прошлых низких баллов и эффект исправления на скрытом наборе неизвестны.
- Изменения не ослабляют проверку источников и не подменяют техническую ошибку
  ближайшей цитатой.

Следующие эксперименты с полнотой контекста и формой ответа нужно сравнивать
отдельно; их возможный эффект не приписывается этому исправлению.
