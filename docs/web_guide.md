# Веб-интерфейс юридического ассистента: инструкция для разработчика

Кейс ПСБ «Юридический ассистент», Hack&Change 2026. Репозиторий: `Moonwuk/grounded-legal-rag`.
Составлено 10 ноября 2026 по кейсу (слайды 9–16), Техническому регламенту и коду `main` (коммит `af86471`).

Этот документ объясняет требования и устройство. Пошаговый план работы с командами, стартовым кодом и проверками лежит в `web_roadmap.md`. Если документы расходятся в деталях реализации, верен роадмап.

## 1. Что нужно сделать

Веб-чат, в котором пользователь задаёт юридический вопрос, получает ответ и может открыть документы и конкретные фрагменты, на которые этот ответ опирается. Всё это должно подниматься одной Docker-командой.

Сейчас в репозитории веба нет совсем: есть только пакетный скрипт для лидерборда (`prototype/solution.py`), который читает CSV и пишет CSV.

## 2. Почему это важно

- **Допуск.** Без работающего веб-чата команду не допускают к экспертной оценке: если чата нет, он не запускается или по нему нельзя пройти основной сценарий. Скор LLM-судьи при этом не спасает.
- **Онлайн-этап.** Экспертная оценка даёт 30% балла. В ней «Интерфейс и удобство» весит 15%, «Работоспособность» 20%, «Контроль достоверности» 25% (его жюри тоже увидит через интерфейс).
- **Финал.** «Качество ассистента в живой демонстрации» весит 25%, и демо идёт через веб.

Мелкие недочёты не исключают из оценки, а снижают балл за «Работоспособность». Поэтому сначала рабочий основной сценарий, потом красота.

## 3. Что уже есть в репозитории

Ядро лежит в `prototype/` и написано только на стандартной библиотеке Python, без сторонних пакетов.

| Файл | Что даёт вебу |
|---|---|
| `psb_corpus.py` | `load_corpus(path)` возвращает `(documents, fragments)`. `Document`: `name`, `text`, `sha256`, `quarantined`. `Fragment`: `id`, `document`, `start`, `end`, `text`, `heading`. |
| `psb_retrieval.py` | `Retriever(documents, fragments)`: индекс BM25, строится один раз при старте. |
| `psb_llm.py` | `ProxyClient(deadline)`: клиент модели, читает `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` из окружения. Не больше 4 вызовов на вопрос. |
| `psb_policy.py` | `answer_question(question, retriever, client, top_k)` возвращает `(text, status)`. Внутри поиск, генерация, проверка цитат и отдельный вызов-верификатор. |

Полезные свойства ядра:

- `Fragment.start` и `Fragment.end` — это позиции символов в `Document.text`. Подсветка фрагмента в полном тексте делается точно, без поиска по строке.
- Диалог ядро уже понимает. История передаётся одной строкой в том же формате, что в тестах организаторов:
  ```
  Пользователь: первый вопрос
  Ассистент: первый ответ
  Пользователь: второй вопрос
  ```
- Статусы ответа: `answer`, `partial`, `clarify`, `insufficient`, `out_of_scope`, `disallowed`, плюс служебные `unverified` и `technical_error`.
- База знаний лежит в `organizer/knowledge-base.zip` (21 документ). В имени файла зашиты категория и статус: `законы__ТК_ст99_действующая.txt`, `документы компании__Регламент согласования договоров ред 2023 (утратил силу).txt`.

## 4. Главная техническая задача: структурированный ответ

`answer_question` отдаёт только готовый текст, где источники вшиты строками вида `[1] Название: «цитата».` Для интерфейса этого мало: нужны идентификаторы фрагментов и их позиции.

Рекомендуемое решение: выделить в `psb_policy.py` функцию, которая возвращает структуру, а `answer_question` оставить тонкой обёрткой над ней. Тогда поведение сабмита не меняется, а веб и лидерборд гарантированно используют одну логику. Все нужные данные внутри функции уже есть: `candidate`, `evidence`, `source_gaps`.

Предлагаемый формат ответа бэкенда:

```json
{
  "status": "partial",
  "text": "итоговый текст, тот же, что уходит в submission.csv",
  "sources": [
    {
      "n": 1,
      "document_id": "sha256 файла документа",
      "title": "Договор поставки П-17-2024 Альфа-Трейд",
      "heading": "5.2. …",
      "start": 1840,
      "end": 2010,
      "quote": "точный текст фрагмента"
    }
  ],
  "elapsed_seconds": 37.2
}
```

Правка затрагивает `prototype/`, то есть код сабмита. Согласуйте её с тем, кто ведёт ядро, и после неё прогоните `python3 -m unittest discover -s tests -v` и `python3 build_submission.py`.

Запасной вариант без правки ядра — разбирать готовый текст и искать цитаты в документах. Он хрупкий, потому что текст цитаты нормализуется перед выводом. Используйте его только если ядро трогать нельзя.

## 5. Минимальный API

| Метод | Назначение |
|---|---|
| `POST /api/chat` | Принимает историю сообщений, склеивает её в строку формата «Пользователь: / Ассистент:», вызывает ядро, возвращает JSON из раздела 4. |
| `GET /api/documents` | Список документов: идентификатор, заголовок, категория, статус. |
| `GET /api/documents/{id}` | Полный текст документа. Идентификатор — `sha256` файла (`Document.sha256`). Ищите документ по словарю загруженных документов, не подставляйте значение в путь файла. |
| `GET /healthz` | Проверка, что сервис поднялся и индекс построен. |

Корпус и `Retriever` создаются один раз при старте. На каждый запрос создаётся свой `ProxyClient(deadline=time.monotonic() + N)`. Историю диалога храните на клиенте или в сессии, но не в общем состоянии между пользователями.

## 6. Интерфейс

**Экран.** Слева чат, справа панель документа. Клик по номеру источника `[1]` открывает документ справа, прокручивает к фрагменту и подсвечивает его. Отдельно доступен список всех документов базы.

**Время ответа.** В последнем прогоне на 18 демо-вопросах выходило около 40 секунд на вопрос (340 секунд при двух потоках). Нужен явный индикатор ожидания, блокировка повторной отправки и понятное сообщение при таймауте. Сервер не должен зависать на одном запросе.

**Статусы.** Каждый статус должен выглядеть по-своему, это прямо показывает жюри контроль достоверности:

| Статус | Как показать |
|---|---|
| `answer` | Ответ и список источников. |
| `partial` | Ответ, источники и заметная пометка «подтверждена только часть», плюс чего не хватает. |
| `clarify` | Уточняющий вопрос. Следующая реплика пользователя уходит вместе с историей. |
| `insufficient` | Обоснованный отказ: в базе нет оснований, какой документ нужен. |
| `out_of_scope` | Вежливое сообщение о границах компетенции. |
| `disallowed` | Отказ помогать с противоправным действием. |
| `unverified` | Ответ не прошёл проверку, предложить уточнить вопрос. |
| `technical_error` | Техническая ошибка и кнопка «Повторить». Не показывать это как «в базе нет сведений». |

**Карточка источника и документ.** Показывайте название, пункт или статью (`heading`), цитату и статус документа: «действующая», «утратил силу», «допсоглашение». В базе специально заложены ловушки: регламент 2023 года (утратил силу) рядом с редакцией 2025, допсоглашение № 1 к договору П-17/2024, похожие контрагенты «Альфа-Трейд» и «Альфа-Трейдинг». Пометка статуса сразу показывает, что ассистент различает редакции.

**Дополнительно, если останется время:** примеры вопросов на пустом экране, кнопка «Новый диалог», поиск по тексту документа, время ответа под сообщением.

## 7. Запуск и состав сдачи

Требования кейса (слайд 11):

- `Dockerfile`, `compose.yaml` и `.dockerignore`: все компоненты запускаются одной командой.
- `README.md`: назначение и архитектура, команда запуска, переменные окружения, порты, зависимости, порядок проверки основного сценария, известные ограничения.
- Файл зависимостей с зафиксированными версиями.
- `.env.example` без действующих ключей. Для внешнего API в README указать сервис, модель, имя переменной и порядок подключения ключа.
- На первом слайде презентации: порядок проверки, ссылка на репозиторий и, если есть, ссылка на развёрнутый интерфейс.

Что это значит для текущего репозитория:

1. Положите веб в отдельный каталог, например `web/`, со своим `Dockerfile` и `requirements.txt`.
2. Создайте `compose.yaml` в корне репозитория. Целевая команда: `docker compose up --build`, после неё чат открывается на `http://localhost:<порт>`.
3. Создайте `web/Dockerfile.dockerignore`. Корневой `.dockerignore` пропускает в сборку только `prototype/` и `containers/`, и без отдельного файла Docker не увидит каталог `web/`.
4. Базу знаний (`organizer/knowledge-base.zip`) смонтируйте в контейнер как файл только для чтения.
5. Добавьте корневой `.env.example` с `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` и портом.

## 8. Ограничения, о которые легко споткнуться

- **Не трогайте `deploy/compose.yml` и корневой `Dockerfile`.** Это пакетный контейнер, и CI (`check_deployment.py`) требует, чтобы в том compose был ровно один сервис `psb` с жёстким набором полей. Сервис с портами туда добавить нельзя.
- **Не добавляйте сторонние импорты в `prototype/`.** Проверка зависимостей считает этот каталог рабочим кодом сабмита и ждёт, что он остаётся на стандартной библиотеке. Зависимости веба держите в `web/`.
- **Образ.** Пакетный образ собран на `python:3.15-alpine` без `pip`. Для веба проще взять отдельный базовый образ со стабильной версией Python, под которую есть готовые сборки нужных библиотек.
- **Модель.** В финальном прототипе должна использоваться та же модель, что на платформе: DeepSeek V4.1 Flash. Имя модели берётся из окружения, в коде его не фиксируйте.
- **Ключ.** Только через окружение или файл секрета. Ключ не должен попадать в браузер, логи, репозиторий и образ.
- **Экранирование.** Тексты документов и ответы вставляйте в страницу только как текст, без `innerHTML`. В документах базы есть строки, похожие на инструкции, это тоже проверка.
- **Логи.** По правилам репозитория в логи не пишутся промпты, тексты источников, ответы API и секреты.
- **Никаких внешних источников.** Веб не должен ходить в интернет за правовой информацией. Ссылки `URL:` в шапках законов можно показать как реквизит, но не как основание ответа.
- **Процесс.** Работа в отдельной короткой ветке, изменения через PR, `Security gate` должен пройти. Подробности в `AGENTS.md`, разделы 1 и 6.

## 9. Порядок работы

1. **Каркас.** Сервис, который при старте загружает корпус и отвечает на `POST /api/chat` текстом из `answer_question`. Один экран с полем ввода. Compose и запуск одной командой. Этого уже достаточно для допуска.
2. **Источники.** Структурированный ответ из раздела 4, карточки источников, панель документа с подсветкой.
3. **Диалог и статусы.** История, уточняющие вопросы, отдельный вид для каждого статуса, индикатор ожидания, обработка ошибок.
4. **Сдача.** README, `.env.example`, проверка запуска на чистой машине, развёрнутая копия и ссылка на неё.
5. **Полировка.** Пометки статуса документов, примеры вопросов, внешний вид.

Стек кейс не ограничивает. Практичный вариант: бэкенд на FastAPI и фронт на обычном HTML и JS без сборки, потому что двухпанельный экран с подсветкой фрагмента там делается проще, чем в Streamlit. Streamlit быстрее на первом шаге, но хуже подходит для просмотра документов.

## 12. Что решить с командой

- **Как жюри получит доступ к модели.** Прокси организаторов доступен только на платформе. Для локального запуска жюри понадобится ключ, которого в репозитории быть не может. Надёжнее всего развернуть интерфейс и дать ссылку на первом слайде. Уточните у организаторов, как они будут проверять.
- **Кто правит `psb_policy.py`** под структурированный ответ: веб-разработчик или владелец ядра.
- **Где разворачивать** демо-копию и кто отвечает за её работу во время защиты.
