# grounded-legal-rag

Юридический RAG-ассистент для кейса ПСБ на Hack&Change 2026. Пользователь задаёт вопрос по базе документов, получает ответ с дословными основаниями и открывает соответствующий фрагмент в полном тексте. Если сведений недостаточно, ассистент запрашивает уточнение или объясняет пробел; техническая ошибка показывается отдельно.

Проект включает **веб-интерфейс для демонстрации** и **пакетное решение для конкурсной платформы**. Они используют одно ядро поиска и проверки ответов в `prototype/`. Интернет не используется как дополнительная юридическая база: источником служит переданный корпус.

**Демо:** <https://legal.77-221-140-87.sslip.io> — требуется выданный командой логин и пароль. Учётные данные и API-ключи в репозиторий не включаются. Адрес временный; воспроизводимый локальный запуск описан ниже.

## Быстрый старт: веб-чат

Нужны Git, Docker Engine или Docker Desktop с **Docker Compose v2**, свободный порт `8000` и доступ к интернету для первой сборки. Python и Node.js на хосте для Docker-запуска не нужны. Compose ограничивает контейнер 2 GiB памяти и двумя CPU; оставьте ресурсы также для Docker и системы.

Клонируйте репозиторий с доступом к нему и перейдите в каталог:

```bash
git clone https://github.com/Moonwuk/grounded-legal-rag.git
cd grounded-legal-rag
```

Для финальной сдачи используйте зафиксированный коммит. Запуск из корня проекта — одной командой:

```bash
docker compose up --build -d --wait
```

Откройте <http://127.0.0.1:8000>. Каталог и просмотр документов доступны сразу. В комплекте используется `organizer/knowledge-base.zip`: 21 документ, 1113 фрагментов в проверенной версии корпуса. Без API-ключа приложение сообщает, что модель не настроена; содержательных ответов в этом режиме нет.

Для подключения модели создайте локальный файл настроек, **если `.env` ещё не существует**:

```bash
cp .env.example .env
chmod 600 .env
```

Заполните в нём три переменные. Для текущего демо на публичном DeepSeek:

```dotenv
LLM_BASE_URL=https://api.deepseek.com
LLM_API_KEY=<ваш API-ключ>
LLM_MODEL=deepseek-flash
```

Значение в угловых скобках замените реальным ключом. Для конкурсного запуска укажите **адрес, ключ и идентификатор модели, выданные организаторами**. Работа публичного DeepSeek не подтверждает совместимость с конкурсным прокси. Модель выбирается окружением, скрытой подмены провайдера нет.

Примените настройки:

```bash
docker compose up -d --wait
```

После изменения `.env` нужен `up`, чтобы Compose пересоздал контейнер с новым окружением; один `restart` настройки не перечитывает. Доступ к модели должен быть с сервера. Ключ остаётся на сервере и не передаётся в браузер.

| Режим | Что доступно |
|---|---|
| Без модели и без прокси | Интерфейс, каталог, поиск по названиям, просмотр документов и четыре готовых шаблона вопросов |
| С моделью, без авторизующего прокси | Ответы, источники и готовые шаблоны; диалог хранится только в памяти открытой вкладки браузера |
| С моделью, авторизующим прокси и серверной историей | Сохранённые диалоги и ветки, папки, корзина, свои подборки, карточки дел с задачами, избранное, заметки, черновики, свои шаблоны, справки, отметки проверки, сохранённые поиски, недавние документы, остановка и очередь; доступ с разных устройств |

Корневой `compose.yaml` собирает **`web/Dockerfile`**. Корневой `Dockerfile` предназначен для отдельной пакетной задачи и не запускает сайт.

## Проверка основного сценария

1. Откройте сайт и раздел документов. На вкладке «Все» должен появиться каталог; найдите договор аренды с ООО «Северный Склад».
2. Задайте вопрос: **«Какова арендная плата по договору с ООО „Северный Склад“?»**
3. Проверьте смысл ответа по исходному договору: **450 000 рублей в месяц, включая НДС, пункт 3.1**. Формулировка модели может различаться; обязательны корректное основание и отсутствие выдуманных условий.
4. Нажмите карточку источника. Откроется документ с выделенным фрагментом. Сопоставьте цитату и ответ с полным текстом.
5. Продолжите диалог уточняющим вопросом. Для неоднозначного вопроса проверьте запрос уточнения; для отсутствующих в базе сведений — объяснение недостатка данных.
6. На телефоне проверьте ввод, открытие истории и документов из шапки и возврат к ответу.

При включённой серверной истории дополнительно:

- Создайте и переименуйте диалог, поместите его в папку. Откройте сайт на другом устройстве под тем же логином и обновите список.
- Во время ответа отправьте ещё два вопроса, поменяйте их порядок кнопками «Выше»/«Ниже», остановите ответ и продолжите очередь.
- Создайте свою вкладку документов через фильтры типа, редакции и названия. Убедитесь, что выбор сохранился после перезагрузки.
- Переместите тестовый диалог в корзину, восстановите его с источниками; затем проверьте окончательное удаление и отмену подтверждения на отдельном ненужном диалоге.

Пять новых инструментов проверяются на том же тестовом диалоге:

1. **Шаблон.** Откройте «Шаблоны», выберите «Редакция на дату», укажите договор и дату. Проверьте итоговый текст и перенесите его в поле ввода: вопрос должен остаться черновиком до нажатия «Отправить».
2. **Справка.** После получения двух ответов нажмите «Собрать справку», выберите оба, поменяйте порядок и добавьте комментарий. Сверьте полный текст и источники в предпросмотре, сохраните справку и проверьте печать / PDF.
3. **Моя проверка.** Отметьте ответ как требующий дополнительной проверки. Найдите его соответствующим фильтром в «Избранном и заметках»; статус самого ответа должен остаться прежним.
4. **Поиски и недавние документы.** Сохраните запрос в каталоге, измените поиск и примените сохранённый. В подборе документов сохраните фильтры и убедитесь, что их применение не снимает выбранные документы. Откройте документ и найдите его в «Недавних».
5. **Задачи.** В карточке дела создайте задачу, добавьте комментарий и ссылки на документ и избранный ответ. Проверьте отметку выполнения, фильтры и порядок. При создании ветки выберите копирование задач: отметки выполнения и ссылки на ответы исходного диалога не должны переноситься.

Обновите страницу или откройте сайт на другом устройстве под тем же логином: сохранённые материалы должны загрузиться с сервера. Работа самих этих инструментов не вызывает модель; генерацию запускает только отправка вопроса.

Состояние локального сервиса:

```bash
curl --fail http://127.0.0.1:8000/healthz
```

Ответ содержит `status`, число `documents` и `fragments`, состояние `dense` и сведения `skipped`. Это проверка загрузки приложения и корпуса, **не проверка доступности LLM**. В публичном демо служебный `/healthz` закрыт прокси и возвращает 404.

## Возможности интерфейса

Ниже перечислены реализованные возможности веба. Это список для проверки продукта и подготовки презентации; качество юридических выводов оценивается отдельно. Для личных материалов и доступа с разных устройств — истории, папок, очереди, подборок, карточек дел с задачами, избранного, заметок, черновиков, своих шаблонов, справок, отметок проверки, сохранённых поисков и недавних документов — нужны авторизующий прокси и включённая история, как описано в [настройке доступа](#серверная-история-и-внешний-доступ).

### Ответы, основания и уточнения

- **Источники в ответе.** Нумерованные ссылки ведут к конкретным положениям документов. Выдержки одного документа объединяются под общим заголовком; каждый фрагмент сохраняет отдельный переход.
- **Проверка цитаты в контексте.** Можно развернуть выдержку, открыть полный извлечённый текст с подсветкой основания и скопировать точную цитату.
- **Явный результат обработки.** Интерфейс различает ответ, частичный ответ, необходимость уточнения, недостаток сведений, непрофильный запрос, отказ, неподтверждённый результат, техническую ошибку и остановку. Статус приходит от сервера; оформление не доказывает правильность вывода.
- **Уточнение через форму.** Для «Нужно уточнение» показаны поля недостающих сведений и кнопка «Продолжить». Поля берутся из словаря приложения; для старой истории без метаданных есть общее поле. Замена существующего черновика требует подтверждения.
- **Примеры вопросов на старте.** Пользователь может начать с предложенного вопроса по корпусу, затем продолжить обычный диалог.

### Документы и собственные подборки

- **Каталог по разделам:** «Все», «Законы», «Договоры», «Регламенты», «Прочее». Основные вкладки расположены без горизонтальной прокрутки, показывают число документов; поиск по названию работает внутри выбранного раздела.
- **Свои вкладки.** Пользователь собирает подборку из существующей базы, задаёт название, меняет состав или удаляет подборку. Удаление подборки не удаляет документы. После изменения на другом устройстве список можно обновить.
- **Фильтры выбора:** название, тип — включая допсоглашения, редакция и «Только выбранные». Есть счётчик выбора и сброс фильтров; скрытие документа фильтром не снимает его отметку. Редакция берётся из метаданных, а не проверяется в интернете.
- **Сохранённые поиски.** В каталоге сохраняются выбранная вкладка и запрос; в подборе документов — запрос, тип, редакция и фильтр «Только выбранные». Поиск можно применить, переименовать или удалить. Применение работает по текущей базе и не меняет состав выбранных документов. Если сохранённая вкладка удалена, показано сообщение о недоступности.
- **Недавние документы.** Последние 20 уникальных открытых документов доступны под тем же логином на разных устройствах. Повторное открытие поднимает документ в списке; недоступный документ сохраняет соответствующую отметку. Список можно очистить без удаления документов или диалогов.
- **Полный текст и поиск внутри него.** Совпадения подсвечиваются; доступны переходы ↑/↓, Enter / Shift+Enter и возврат «К цитате». Возврат к каталогу сохраняет выбранный раздел и поиск.
- **Позиция чтения.** Сохраняется в текущем браузере; при открытии источника из ответа переход к цитате имеет приоритет.
- **Вопрос по выделению.** Кнопка «Спросить о выделенном» открывает форму с точным фрагментом. Можно ввести свой вопрос либо выбрать «Объяснить пункт» или «Условия и исключения». Название документа, выделение и вопрос добавляются в видимый черновик; пользователь сам отправляет его.

Подборки организуют просмотр, **но не ограничивают поиск ассистента**: ответ строится по всему корпусу. Загрузки новых файлов через веб и режима просмотра двух документов рядом нет. Подробности — [вкладки документов](docs/document_tabs.md) и [рабочие материалы](docs/web_workspace.md).

### Диалоги, папки и ветки

- **Серверная история.** Хранятся вопросы, ответы, статусы и источники. Под одним логином они доступны с разных устройств; завершённый ответ сохраняется и при закрытой вкладке браузера.
- **Новый диалог и переименование.** Новый диалог создаётся в выбранной папке. Название, заданное вручную, не заменяется после нового ответа.
- **Поиск и закрепление.** Поиск учитывает названия, вопросы и ответы; выбранная папка ограничивает список. Важные диалоги можно закрепить над остальными.
- **Папки.** Можно создавать, переименовывать и удалять папки, перемещать в них диалоги. Удаление папки сохраняет диалоги в разделе «Без папки».
- **Корзина.** Диалог можно восстановить с его источниками или окончательно удалить после подтверждения. Автоматической очистки корзины нет; удаление из интерфейса не стирает существующие резервные копии.
- **Новые ответы.** У другого диалога появляется отметка «Новый ответ». Состояние прочтения хранится на сервере; обновление активности происходит периодически на видимой странице, это не системные push-уведомления.
- **Правка вопроса через ветку.** Изменение старого вопроса создаёт отдельный диалог с предшествующей историей и исправленным вопросом в черновике. Исходный диалог остаётся целым.
- **Продолжение от выбранного ответа.** «Продолжить в ветке» копирует историю до этого ответа включительно. Последующие сообщения не переносятся. Есть переход к исходному диалогу; ветка наследует карточку дела и папку, но не заметки, избранное, справки или отметки проверки. Задачи копируются только при выбранной опции, без отметок выполнения и ссылок на ответы исходного дела. Создание ветки само по себе не вызывает модель.

Действия собраны в компактном меню `⋯`. Папки и диалоги используют одну область прокрутки. Подробности — [история](docs/chat_history.md) и [ветки](docs/web_workspace.md).

### Карточка дела, задачи, избранное, заметки и черновики

- **Карточка дела.** Хранит договор, контрагента, дату события, сумму и обстоятельства. «Добавить в вопрос» явно вставляет заполненные сведения в поле ввода; автоматической отправки нет.
- **Задачи дела.** В раскрываемом разделе «Задачи» можно вести до 40 пунктов: название, комментарий, отметка выполнения, ссылка на документ и сохранённый ответ этого диалога. Есть редактирование, удаление, перемещение выше/ниже и фильтры «Все», «Осталось», «Выполнено». Это личный список действий; отметка выполнения не проверяет юридический вывод автоматически.
- **Избранные ответы.** Отметку можно поставить или снять у конкретного ответа. Из общего списка доступен переход обратно к ответу с источниками и копирование с основаниями.
- **Личные заметки.** Привязаны к конкретному сохранённому ответу, отображаются отдельно от его текста и источников. В панели «Избранное и заметки» есть поиск по вопросу, ответу и заметке, фильтры «Всё сохранённое», «Избранные ответы», «С заметками».
- **Черновики.** Сохраняются отдельно для каждого диалога и ещё не созданного диалога. Индикатор сообщает результат записи на сервер; перед переключением ожидается сохранение. При мгновенном закрытии браузера до завершения записи последние изменения могут не сохраниться.
- **Работа с двух устройств.** Проверка версий защищает от молчаливой перезаписи. Для конфликта черновиков показаны обе версии и выбор пользователя; при конфликте карточки или заметки нужно загрузить свежую версию перед повторным сохранением.

Карточка, задачи и заметки **не передаются модели автоматически** и не становятся юридическими источниками. В корзине рабочие материалы скрыты; восстановление возвращает их вместе с диалогом. Окончательное удаление диалога удаляет его связанные рабочие данные. Подробности — [рабочие материалы веба](docs/web_workspace.md).

### Шаблоны вопросов, справка из ответов и отметки проверки

- **Шаблоны вопросов.** Кнопка «Шаблоны» рядом с полем ввода открывает готовые шаблоны и свои шаблоны с поиском. Поля `{договор}`, `{контрагент}`, `{дата}`, `{сумма}`, `{уточнение}` заполняются вручную или из карточки дела; итоговый вопрос виден и редактируется до переноса в поле ввода. Незаполненное обязательное поле блокирует перенос, неизвестные значения не подставляются. Свой шаблон можно создать, изменить, скопировать, удалить или сохранить из своего вопроса в диалоге. Отправку выполняет пользователь.
- **Справка из ответов.** «Собрать справку» объединяет выбранные готовые ответы диалога в заданном порядке с источниками каждого раздела. Ответы и цитаты приводятся полностью; вступление, комментарии к разделам, сведения карточки и отметки подписаны как пользовательские. Справку можно скопировать, распечатать или сохранить в PDF через окно печати, сохранить и открыть позже. Изменённый после сборки ответ помечается недоступным, а не подменяется.
- **Личные отметки проверки.** Под ответом пользователь выбирает «Не проверено мной», «Источники просмотрены» или «Нужна дополнительная проверка». Отметка показывает дату, синхронизируется между устройствами, фильтруется в панели «Избранное и заметки» и не меняет статус ответа системы.

Четыре готовых шаблона — «Согласование договора», «Сроки и обязательства», «Редакция на дату», «Основания вывода» — доступны и без серверной истории. Подстановка из карточки выполняется по кнопке и заполняет только пустые поля. Справка хранит ссылки на конкретные версии ответов: при недоступном разделе его нужно убрать, прежде чем сохранять, копировать или печатать справку. Ответы с технической ошибкой или остановкой в неё не включаются. Отметка «Источники просмотрены» недоступна у ответа без источников.

Эти функции не вызывают модель, не расходуют квоту вопросов и не добавляют данные в её контекст. Подробности, пределы и проверки — [шаблоны, справка и отметки](docs/web_answer_tools.md).

### Остановка и управление очередью

- Пока готовится ответ, можно отправить следующие вопросы. Они сохраняются на сервере и выполняются последовательно с контекстом завершённых ответов.
- Ожидающий вопрос можно **отредактировать, переместить выше или ниже, удалить**. Если он уже начал обрабатываться, устаревшая правка отклоняется.
- **«Остановить»** прерывает текущий обработчик и ставит очередь на паузу; вопрос и статус остановки остаются в истории.
- **«Продолжить»** запускает оставшиеся вопросы. Повтор остановленного ответа — новая попытка, а не дописывание оборванного текста.
- При технической ошибке зависимые вопросы приостанавливаются; доступен повтор. Очередь и история не зависят от открытой вкладки, но остановка самого сервера может прервать текущую попытку.

Остановка закрывает соединение приложения, но не гарантирует отмену обработки и начислений у провайдера. Лимиты очереди приведены в [ограничениях](#ограничения); реализация — [очередь вопросов](docs/question_queue.md).

### Копирование, пересылка и печать

- **Копирование ответа с источниками** сохраняет полный текст и цитаты. При недоступном буфере открывается окно приложения для ручного копирования.
- **«Поделиться»** передаёт выбранный ответ с источниками в системное меню браузера/устройства. Если оно недоступно, предлагается копирование; встроенной отправки писем или сообщений в мессенджер нет.
- **Печать диалога / PDF** включает текущий диалог. **Печать документа / PDF** включает весь извлечённый текст документа, а не только видимый фрагмент. Сохранение PDF выбирается в системном окне печати; исходное оформление DOCX не воспроизводится. Печать использует светлое оформление независимо от темы сайта.

Подробности и браузерные сценарии — [работа с ответами и поиск](docs/web_usability.md).

### Мобильная компоновка и доступность

- На телефоне основное место занимает диалог, поле ввода расположено снизу; история и документы открываются отдельными панелями из шапки. Новый диалог доступен из основной шапки, из источника можно вернуться к ответу.
- На компьютере панель документов можно свернуть. Ширина истории учитывает размер текста; меню действий и папки используют компактные строки.
- Enter отправляет вопрос, Shift+Enter добавляет строку. Вкладки документов поддерживают стрелки, Home и End; предусмотрены видимый клавиатурный фокус и доступные названия иконок. Окна можно закрывать Escape, кроме момента сохранения, когда закрытие блокируется.
- Формы и подтверждения сделаны окнами приложения, а не `alert`/`prompt`/`confirm`. Печать и системная пересылка используют штатные окна браузера или устройства.
- У знакомых действий есть SVG-иконки и подсказки; для иконок и действий истории на сенсорных устройствах предусмотрены области нажатия не менее 44 px.

Проверены браузерные сценарии на размерах 1440×1000, 390×844, 320×568 и 390×420, в том числе с тёмной темой и текстом 22 px. Это не сертификация доступности: полный аудит экранным диктором и проверка экранной клавиатуры физического телефона отдельно не заявлены. Подробнее — [мобильный интерфейс](docs/mobile_ui.md).

### Оформление и анимации

- **Три режима темы:** светлая, тёмная, системная с отслеживанием изменения настройки устройства.
- **Шесть акцентов:** синий ПСБ, фиолетовый, изумрудный, оранжевый, розовый, графитовый.
- **Пять шрифтов:** Georgia, Arial, Inter, Roboto, Times New Roman. Inter и Roboto поставляются локально; остальные используют доступные системные шрифты с запасным семейством.
- **Размер текста 12–22 px**, быстрые значения 14, 16 и 20 px, предпросмотр и сброс к стандартному оформлению.
- **Анимированный персонаж** показывает поиск и реакции на результат: подтверждённый или частичный ответ, уточнение, нехватку данных, непрофильный/недопустимый запрос, неподтверждённый результат, техническую ошибку, остановку. Для защиты роли есть отдельное отображение при соответствующем сигнале сервера. В истории сохраняется кадр состояния; новый результат проигрывает реакцию один раз.
- **Отключение анимаций** и уважение системного уменьшения движения. Отправка и копирование также имеют визуальную обратную связь. У страницы есть собственная иконка вкладки браузера — favicon.

Оформление сохраняется **в текущем браузере**, не в аккаунте. Анимация сообщает состояние, но не заменяет проверку текста и источников. Подробности — [настройки оформления](docs/APPEARANCE_SETTINGS.md), [анимация](docs/web_animation.md) и [состояния персонажа](docs/UI_ANIMATIONS.md).

### Где сохраняются данные и что показывать на защите

| Данные | Где хранятся и как доступны |
|---|---|
| Диалоги, папки, корзина, закрепления, очередь, свои подборки | SQLite на сервере, разделены по логину авторизующего прокси |
| Карточки дел, избранное, заметки, черновики, отметки прочтения, свои шаблоны вопросов, справки, отметки проверки | На сервере под тем же логином; для редактируемых рабочих материалов проверяются версии |
| Сохранённые поиски и недавние документы | На сервере по логину; параметры поиска и история открытия, без копий документов |
| Задачи карточки дела | На сервере в составе диалога; сохраняются в корзине и удаляются окончательно вместе с ним |
| Тема, акцент, шрифт, размер, настройка анимаций, позиция чтения | Локально в браузере; на другое устройство автоматически не переносятся |
| Документы корпуса | Общая база, подключённая оператором; отдельных прав по документам или ролям нет |

Один общий логин означает общие рабочие данные. Самостоятельной регистрации, администрирования аккаунтов и ролевого разграничения документов нет. В кейсе отдельные аккаунты и роли доступа не указаны как обязательные; «Соответствие роли» на стр. 8 относится к поведению ассистента. Эти механизмы можно обсуждать как развитие для внедрения, но не представлять реализованными. Основания — [требования организаторов](docs/organizer_requirements.md).

Для короткой демонстрации на тестовых данных: **шаблон → вопрос → источник и подсвеченная цитата → личная отметка проверки → задача в карточке дела → справка с источниками → открытие сохранённых материалов на другом устройстве**. На дополнительных слайдах можно показать выделение фрагмента, ветки, очередь и остановку, сохранённые поиски, подборки, корзину и оформление. Реальные вопросы расходуют лимиты API; браузерные тесты с заглушками подтверждают работу интерфейса, а не юридическое качество модели.

## Серверная история и внешний доступ

Для полноценного режима нужны HTTPS, аутентификация на обратном прокси и отдельный логин для каждого пользователя. Встроенной регистрации пользователей, восстановления паролей и MFA в приложении нет.

1. Сгенерируйте случайный секрет, например `openssl rand -hex 32`, и сохраните его как `CHAT_PROXY_TOKEN` в приватном `.env`. Тот же секрет передайте окружению прокси, не публикуя его в Git.
2. Настройте HTTPS и вход для **всего сайта**, включая API и статику. В текущем демо используется Caddy с Basic Auth.
3. После успешного входа прокси должен **перезаписывать** `X-Chat-User` проверенным логином и `X-Chat-Token` общим секретом. Значения, присланные браузером, доверенными не являются.
4. Сохраните исходный `Host`, удалите `Authorization` перед передачей в приложение и оставьте порт приложения на `127.0.0.1`. Закройте извне `/healthz`, `/docs`, `/redoc` и `/openapi.json`.
5. Выполните `docker compose up -d --wait` и проверьте вход, сохранение диалога и доступ с другого устройства. Без входа API не должен возвращать данные.

Фрагмент для Caddy **внутри `reverse_proxy` после настроенного `basic_auth`**:

```caddyfile
header_up X-Chat-User {http.auth.user.id}
header_up X-Chat-Token {env.CHAT_PROXY_TOKEN}
header_up -Authorization
```

Это часть конфигурации, а не готовый Caddyfile: домен, TLS, пользователи и закрытие служебных маршрутов настраиваются оператором. Переменная должна быть в окружении самого Caddy; `.env` приложения не передаётся ему автоматически. Если прокси находится в отдельном контейнере, его `127.0.0.1` не является адресом хоста — требуется соответствующая сетевая конфигурация.

После включения истории все `/api/*` требуют проверенную пару логин/секрет. Чужие диалоги, папки и подборки недоступны. Один общий логин означает общую историю: для изоляции нужны разные логины на прокси.

Прокси текущего демо настроен отдельно от репозитория. Сам `docker compose up` не создаёт публичный домен и не настраивает вход. Подробности хранения и API — [история диалогов](docs/chat_history.md).

## Архитектура и контроль достоверности

```text
Браузер → HTTPS / авторизующий прокси → FastAPI
                                         ├─ SQLite: диалоги, очередь, квоты, личные материалы
                                         └─ ядро RAG
                                             ├─ корпус → фрагменты → поиск
                                             ├─ API модели → кандидат ответа
                                             └─ проверки → ответ, статус, источники
```

При старте сервер читает архив корпуса, извлекает документы и строит поисковый индекс. BM25 дополнен обработкой номеров положений, названий, связанных документов и редакций; эмбеддинги подключаются опционально. Тестовые вопросы и эталоны в рабочий индекс не входят.

Модель получает найденные положения и формирует кандидат ответа. Ядро проверяет существование источников, дословность цитат, числа, даты, расчёты, ссылки на положения и ограничения вывода. В веб-режиме предусмотрен отдельный проверяющий вызов модели; при непрошедшем контроле свободный текст не публикуется как подтверждённый вывод. В batch отдельный верификатор по умолчанию выключен ради бюджета — программные проверки остаются.

Браузер получает текст, статус и структурированные источники: документ, цитату и позиции символов в извлечённом тексте. По этим позициям открывается и подсвечивается основание. Возможны полный или частичный ответ, уточнение, недостаток сведений, выход за границы задачи, отказ и техническая ошибка. Проверка совпадения цитаты сама по себе не доказывает правильность юридического вывода.

Серверная история восстанавливается из SQLite по владельцу диалога. Очередь запускает генерацию в отдельном процессе, что позволяет остановить обработчик и соединение с провайдером. SQLite хранит завершённые ответы и ожидающие вопросы; история не зависит от открытой вкладки браузера.

Стек: Python, FastAPI/Uvicorn, SQLite, HTML/CSS/JavaScript без отдельной frontend-сборки. Ядро `prototype/` использует стандартную библиотеку Python. Зависимости веба закреплены в [web/requirements.txt](web/requirements.txt), базовый Docker-образ — по digest. Подробности — [архитектура RAG](docs/rag_architecture.md), [проверка текста](docs/prose_safety.md), [границы доказательств](docs/evidence_boundary_fix.md).

## Эксплуатация и диагностика

Команды выполняются из корня репозитория и относятся к проекту Compose `psb-web`:

```bash
# Состояние и последние сообщения сервиса
docker compose ps
docker compose logs --tail=100 web

# Пересобрать и применить выбранную версию исходников
docker compose up --build -d --wait

# Остановить, сохранив данные
docker compose stop

# Запустить остановленный сервис
docker compose start
```

Корпус подключён только для чтения. Его замена выполняется оператором: подготовить совместимый архив, заменить `organizer/knowledge-base.zip`, пересоздать контейнер и проверить загрузку и ответы. Исчезнувшие документы могут сделать старые источники недоступными; пользовательская подборка не является копией документа.

История находится в именованном томе `psb-web_chat-history`. Она переживает пересоздание контейнера и обычный `docker compose down`. **`docker compose down -v` удаляет том и историю** — для обычного обновления эта команда не нужна.

### Обновление и возврат к предыдущему образу

Для ручного обновления демо выберите конкретный commit SHA с успешными Web CI и полным Security gate. Дождитесь завершения вопросов, сохраните резервную копию SQLite по инструкции ниже и перейдите на выбранную версию исходников в чистой рабочей копии. Собирайте новый образ с отдельным именем, чтобы сохранить предыдущий:

```bash
previous_image=$(docker inspect --format '{{.Config.Image}}' "$(docker compose ps -q web)")
release_image="psb-web-web:$(git rev-parse --short=12 HEAD)"
WEB_IMAGE="$release_image" docker compose build web
WEB_IMAGE="$release_image" docker compose up -d --no-build --wait --wait-timeout 90
```

Проверьте healthcheck, вход по HTTPS, старые диалоги и новые функции. После успешной проверки сохраните имя нового образа в `WEB_IMAGE` приватного `.env`, чтобы последующие команды Compose использовали ту же версию. При неуспешной проверке предыдущий образ можно запустить так:

```bash
WEB_IMAGE="$previous_image" docker compose up -d --no-build --wait --wait-timeout 90
```

Возврат образа допустим при совместимой схеме SQLite. Новые таблицы рабочих материалов в релизе `d601a49` добавляются без переписывания старых диалогов; это не обещание совместимости будущих миграций. Восстановление базы из копии — отдельная операция, которая может потерять записи, созданные после копирования.

### Резервная копия истории

При включённой истории можно получить согласованный снимок работающей SQLite через backup API. Следующий пример рассчитан на стандартные пути Compose и создаёт новый файл в текущем каталоге:

```bash
umask 077
backup_file="chats-$(date -u +%Y%m%dT%H%M%SZ).sqlite3"
docker compose exec -T web python -c 'import sqlite3; src=sqlite3.connect("file:/history/chats.sqlite3?mode=ro", uri=True); dst=sqlite3.connect("/tmp/chats-backup.sqlite3"); src.backup(dst); dst.close(); src.close()'
docker compose exec -T web python -c 'import shutil, sys; source=open("/tmp/chats-backup.sqlite3", "rb"); shutil.copyfileobj(source, sys.stdout.buffer); source.close()' > "$backup_file"
chmod 600 "$backup_file"
docker compose exec -T web python -c 'from pathlib import Path; Path("/tmp/chats-backup.sqlite3").unlink()'
```

Копия передаётся через `exec -T`, что работает и с контейнерным `/tmp` на tmpfs. Проверьте успешное завершение команд и перенесите файл в закрытое хранилище вне репозитория. Он содержит диалоги и личные материалы: карточки, задачи, заметки, справки, шаблоны, поиски и историю открытия документов. Для восстановления сначала остановите приложение, сохраните текущий том и восстановите согласованную базу с правами пользователя контейнера `10001:10001`; не заменяйте SQLite работающего сервиса и не смешивайте её со старыми WAL-файлами. Проверяйте восстановление в отдельном окружении до замены рабочей базы.

### Типичные проблемы

| Симптом | Что проверить |
|---|---|
| Модель не настроена | Все три `LLM_*` в `.env`, затем `docker compose up -d --wait` |
| Техническая ошибка модели | URL, идентификатор модели, доступ и квоты провайдера, сетевую доступность с сервера; не публикуйте ключ или полное окружение |
| Нет истории, папок или очереди | `CHAT_PROXY_TOKEN`, доступность SQLite, аутентификацию и перезапись заголовков прокси |
| API возвращает 401 | Проверенный логин и совпадение секрета у прокси и приложения |
| Изменение возвращает 403 | Корректный внешний Host/Origin, обращение с того же сайта |
| Ответ 429 | Квоту вопросов на логин и `Retry-After`; удаление диалогов её не сбрасывает |
| Сервис занят | Число одновременных генераций и `WEB_WORKERS`; дождитесь завершения |
| Контейнер не стартует | `docker compose logs`, наличие файла корпуса, права тома, свободный порт и ресурсы Docker |
| На другом устройстве не видно изменений | Тот же логин; обновите список диалогов или подборок |
| Изменение возвращает 409 | Данные изменились на другом устройстве; сохраните свой текст и загрузите свежую версию. Для черновика доступно окно выбора версий |
| Сохранённый поиск или раздел справки недоступен | Вкладка могла быть удалена, а ответ — заменён; сохранённая ссылка не подставляет другой материал автоматически |
| Публичный `/healthz` возвращает 404 | Это ожидаемая защита демо; проверяйте healthcheck локально |

Для отдельного управляемого хостинга есть агенты Windows/Linux: [LOCAL_HOSTING](docs/LOCAL_HOSTING.md), [CI/CD](docs/CI_CD.md). Это другой вариант установки; инструкции и исторические сведения о его окружении не описывают автоматически текущее Caddy-демо.

## Безопасность и CI

Приложение и развёрнутое демо проверены в рамках [инженерного аудита от 15.11.2026](docs/web_security_audit_2026_11_15.md) с разбором OWASP. Это ограниченная проверка, а не сертификация или независимый пентест.

| Область | Реализованные меры |
|---|---|
| Доступ | HTTPS и вход на прокси; проверка секрета и владельца объектов на сервере; порт приложения только на localhost |
| Браузер | CSP, запрет framing, nosniff, ограничения Permissions-Policy; проверка Origin/Fetch Metadata для изменяющих API-запросов |
| Данные | Приватные ответы API без кеширования; тексты сообщений и ключи не пишутся в диагностические логи |
| Расход ресурсов | Конечные таймауты, ограничение параллелизма, размеры запросов и контекста; сохраняемые квоты вопросов при серверной истории |
| Контейнер | Non-root UID 10001, read-only root, `cap_drop: ALL`, `no-new-privileges`, tmpfs, отдельный том истории, read-only корпус |
| Ресурсы хоста | По умолчанию 2 GiB RAM, 2 CPU, 128 PID; ротация журналов 3 × 10 MiB |
| Сборка | Закреплённые зависимости и базовый образ; ограниченный контекст сборки через `web/Dockerfile.dockerignore`; ключи и история в образ не входят |

**Сканирование контейнера есть.** [Web CI](.github/workflows/web-ci.yml) на PR и push в `main` запускает регрессии, веб-тесты, проверки JavaScript, сборку/HTTP-проверку контейнера и поиск секретов. Подключённый [web-image workflow](.github/workflows/web-image.yml) проверяет Dockerfile, уязвимости ОС и библиотек образа, а также секреты внутри него. Порог уязвимостей образа — исправляемые HIGH/CRITICAL; ошибка сканера не считается успешным результатом.

[Полный Security scans](.github/workflows/security.yml) работает на `main` раз в два дня и по ручному запуску. В него входят Gitleaks, Bandit, CodeQL, pip-audit, проверки workflow и IaC, Hadolint, Trivy и проверки пакетного контейнера. После успешного общего gate формируется свежий `verified-submission`; это подтверждение перечисленных CI-проверок, а не официального Score. Публикация подписанного пакетного образа включается отдельно. Области анализа и пороги — [security_pipeline](docs/security_pipeline.md).

Наличие CI также не доказывает включённую защиту ветки в настройках GitHub. Для конкурсного воспроизводимого запуска эти дополнительные механизмы не являются отдельным требованием кейса.

## Пакетный сабмит платформы

Пакетный режим читает `questions.csv` и `knowledge-base.zip` из `DATA_DIR`, затем пишет `submission.csv` в рабочий каталог. Контракт — [технический регламент](organizer/technical_regulations_text.md). Платформа передаёт `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` и `DATA_DIR`; ядро также поддерживает альтернативные имена `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL`, `GEN_MODEL`.

Для локального прогона подготовьте каталог данных и передайте настройки модели **через окружение процесса**. Прямой запуск Python сам не загружает `.env` Compose:

```bash
DATA_DIR=/absolute/path/to/data python3 prototype/solution.py
```

Входной CSV содержит `id,question`, выходной — `id,answer`; ID сохраняются как строки. Для примера можно скопировать `organizer/demo_questions.csv` под именем `questions.csv`. `demo_output.csv` служит для сравнения человеком и не читается рабочим решением.

Основные настройки batch: `MAX_WORKERS=2` (максимум 8), `TOP_K=6`, `MAX_TOKENS=8192`, `TEMPERATURE=0`, `PSB_RUN_SECONDS=1100` (максимум 1150). `PSB_VERIFY=1` включает отдельный проверяющий вызов; по умолчанию применяется режим одного вызова с повторами при необходимости. Повторы ограничены числом попыток и общим временем; первая попытка каждого вопроса предшествует повторным попыткам остальных. Транспорт допускает до четырёх попыток на логический вызов; HTTP 429 вводит общую паузу для потоков одного процесса. Полностью технически неудавшийся вопрос может быть поставлен в конец batch-очереди ещё до двух раз в пределах общего дедлайна. Подробности — [смешанные ошибки прокси](docs/mixed_proxy_retries.md), [один вызов в batch](docs/one_call_answers.md), [бюджет и очередь](docs/batch_budget_and_reference_scope.md).

В версии №36 batch без отдельного верификатора также допускает последнюю ограниченную попытку улучшить формулировку ответа, когда уже сохранён проверенный ответ из цитат. Она выполняется после первых двух попыток вопросов и в пределах общего бюджета вызовов; прежний результат заменяется только при улучшении. Веб использует отдельную проверку модели и эту дополнительную попытку `repair_quotes` не включает. Реализация — [answer_steps](prototype/psb_policy.py) и [run_questions](prototype/solution.py), регрессии — [test_terminal_quote_repair.py](tests/test_terminal_quote_repair.py).

При отсутствии конфигурации создаётся CSV с техническими сообщениями, а процесс завершается с кодом 2. Такой файл не является успешным содержательным сабмитом.

Сборка и проверка архива перед отправкой:

```bash
python3 build_submission.py
python3 .github/scripts/check_submission.py
```

Результат — `dist/PSB_baseline_submission.zip`: `solution.py`, необходимые модули и `requirements.txt` в корне, без корпуса, вопросов, эталонов и ключей. В проверенном релизе он совпадает с сохранённым `dist/PSB_36_checked_answers.zip`; хеш приведён в [разделе версии](#конкурсная-версия-и-выкладка). После будущих изменений ядра пересоберите пакет и сверяйте его с текущими исходниками; прежний балл №36 к новому архиву автоматически не относится. [Манифест сборки](results/submission_manifest.json) фиксирует состав, размер и SHA-256, но сам не выполняет прогон платформы. Отдельный batch Docker/IaC описан в [deployment.md](docs/deployment.md) и [infra/ansible/README.md](infra/ansible/README.md).

## Материалы для сдачи

### Что загружать на платформу

Основание: предоставленный PDF кейса «Юридический ассистент», **стр. 11 «Финальная сдача»**; сохранённая выжимка — [требования организаторов, раздел 6](docs/organizer_requirements.md#6-финальная-сдача-сл-11). Для финальной сдачи выбирается **один из двух вариантов**:

| Вариант | Что загружается на платформу | Где находятся код и документация |
|---|---|---|
| PDF + репозиторий | PDF-презентация со ссылкой на репозиторий на первом слайде | Все файлы решения должны быть доступны в указанном репозитории |
| Полный ZIP | Один архив с исходным кодом, документацией и презентацией в PDF | Внутри загружаемого ZIP |

**Презентацию можно хранить и в репозитории**, например в существующем каталоге `docs/`. Это удобная копия общего комплекта, но само наличие PDF в GitHub не заменяет загрузку PDF или полного ZIP на платформу. Отдельный формат «только ссылка на репозиторий» в предоставленном кейсе не указан. Для варианта с репозиторием команда загружает на платформу тот же финальный PDF, который хранит вместе с кодом.

**Пакетный сабмит и финальная сдача — разные комплекты.** Архив `dist/PSB_baseline_submission.zip`, собираемый для автоматического LLM-судьи, содержит пакетное решение. Он не является финальным ZIP проекта с веб-интерфейсом и презентацией. Формат пакетного сабмита описан [выше](#пакетный-сабмит-платформы).

### Содержание презентации и репозитория

На **первом слайде** укажите порядок проверки, ссылку на репозиторий при сдаче через него и, при наличии, адрес развёрнутого интерфейса. Далее кейс требует описать проблему и пользователя, архитектуру, сценарии работы, примеры ответов и отказов, ограничения и идеи развития. Реализованные возможности для слайдов перечислены в [разделе интерфейса](#возможности-интерфейса); планируемые возможности нужно подписывать как планы.

Репозиторий или полный ZIP должен содержать:

- исходники работающего решения;
- README с назначением и архитектурой, одной командой запуска через Docker, переменными окружения, портами, зависимостями, порядком проверки основного сценария и известными ограничениями;

Формат презентации для сдачи — **PDF**. Редактируемый исходник можно сохранить дополнительно, но он не заменяет PDF. Персональные данные в примерах и демонстрации должны быть тестовыми или выдуманными, как требует кейс. Ключи, пароли демо, рабочая `.env`, пользовательская SQLite и резервные копии не входят в материалы сдачи. Доступ к демо нужно согласовать отдельно, не публикуя пароль на слайдах или в Git.

### Проверка перед отправкой

1. Подготовить окончательный PDF, проверить ссылки и основной сценарий по его инструкции. При варианте с репозиторием сохранить копию PDF в `docs/` и добавить ссылку на фактически созданный файл в README.
2. Для приватного репозитория открыть доступ аккаунту жюри **`hack-and-change-2026`**. Наличие публичного демо не заменяет доступ к исходникам.
3. Проверить запуск из чистой копии и работу с предусмотренной организаторами моделью. Совпадение публичного алиаса DeepSeek с конкурсной моделью не считается подтверждённым только по имени.
4. Зафиксировать сдаваемую версию и записать её commit SHA для команды; проверить, что презентация описывает именно эту версию. По кейсу после дедлайна версия фиксируется. Загрузить выбранный PDF или полный ZIP и проверить наличие отправленного файла на платформе.
5. Подтвердить **официальный результат LLM-судьи больше нуля**, работающий основной сценарий веба и полный комплект материалов: это условия допуска на стр. 14 кейса. Локальные оценки и зелёный CI официальный результат не заменяют.

Развёрнутый публичный адрес полезен для демонстрации; обязательна воспроизводимость запуска. Полный автоматизированный production-деплой, продвижение подписанного digest и автоматический rollback отдельно не требуются кейсом.

## Ограничения

- Ответы ограничены предоставленным корпусом. Отсутствующий документ или редакцию нельзя заменить знаниями модели. Актуальность материалов вне корпуса не проверяется.
- Проверки источников и верификатор снижают риск ошибок, но не гарантируют юридическую точность, полноту или устойчивость к любым prompt injection. Нужны независимые смысловые проверки.
- На логин: до 100 активных диалогов, 100 в корзине, 30 папок и 30 подборок. На диалог: до 20 попыток вопроса с учётом резервов очереди; до пяти ожидающих вопросов и до 100 записей заданий за жизнь диалога. Контекст ограничен 30 000 символов, отдельный вопрос — 10 000.
- Личные инструменты: до 50 своих шаблонов и 30 сохранённых поисков суммарно для каталога и подбора на логин; 20 последних уникальных документов; до 40 задач и 20 справок на диалог, до 20 разделов в справке. Сохранённые поиски не ограничивают корпус RAG, а задачи и личные отметки не подтверждают юридическую правильность ответа.
- На ответ выделено до 150 секунд внутри политики; очередь ограничивает процесс вместе с запуском 180 секундами. Остановка закрывает соединение приложения, но не гарантирует прекращение обработки и начислений у провайдера.
- Квоты считают принятые вопросы, а не токены или деньги; работают при серверной истории и сохраняются после перезапуска. Один вопрос может потребовать нескольких вызовов API.
- SQLite не шифруется приложением. Постоянное удаление в интерфейсе не гарантирует физическое стирание из резервных копий и свободных страниц базы. Политику хранения, копирования и удаления задаёт оператор.
- Текущая конфигурация использует один процесс Uvicorn. Горизонтальное масштабирование и распределённая очередь не заявлены; несколько процессов меняют общий предел параллельных обращений к модели.
- Загрузка файлов пользователем, полноценное управление учётными записями, роли и разграничение документов по ролям, MFA и централизованные оповещения безопасности не реализованы.

Результаты внутренних прогонов, включая другие модели и аналог LLM-судьи, — [сводный отчёт](evaluation/reports/STABILITY_AND_FULL_HOLDOUT.md). Это не официальный Score. Проверки равнозначных формулировок и сохранения пояснений описаны в [claim_equivalence](docs/claim_equivalence.md) и [evidence_completeness](docs/evidence_completeness.md); сводка требований — [organizer_requirements](docs/organizer_requirements.md). Дополнительные границы — [архитектура RAG](docs/rag_architecture.md), история версий — [docs/history.md](docs/history.md).
