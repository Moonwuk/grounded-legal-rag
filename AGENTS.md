# AGENTS.md — grounded-legal-rag

Правила для агентов, работающих над юридическим ассистентом ПСБ. Применяются ко всему репозиторию.
Цель изменений — обоснованные ответы по предоставленному корпусу, корректные отказы и воспроизводимый запуск.
Наличие требования в этом файле не означает, что соответствующая функция уже реализована.

## 1. Начало работы и навигация

1. Проверь актуальный `main`, состояние рабочей копии и открытые PR. Используй `git fetch origin main` либо GitHub API с зафиксированным SHA. Не выдавай старую копию за актуальную; при недоступности обновления явно укажи базовую версию и ограничение.
2. Работай в отдельной короткой ветке от актуальной базы. Не удаляй, не перезаписывай и не включай в свой коммит чужие изменения; при занятой рабочей копии используй отдельную.
3. Прочитай [README.md](README.md), выбери область по карте ниже, затем открой профильный документ, код и проверки. Используй `rg` сначала внутри выбранной области; расширяй поиск, когда карта не даёт ответа.
4. После обновления базы заново прочитай затрагиваемые файлы. Определи конкретный результат задачи и способ его проверки до изменения кода.
5. Состояние реализации устанавливай по порядку: код актуального `main` → тесты этого кода → CI того же SHA → открытые PR → документация → старые отчёты и переписка. Требования организаторов определяют ожидаемое поведение независимо от текущей реализации.

## 2. Обязательное поведение по кейсу

- **К01. Только предоставленная база.** Юридические основания берутся из корпуса организаторов. Интернет, внешние правовые базы и знания модели не могут дополнять основания ответа. Изучение технологий при разработке не меняет этого ограничения runtime.
- **К02. Проверяемые выводы.** Каждое юридически значимое утверждение связывай с существующим документом и конкретным подтверждающим положением. При необходимости сопоставляй несколько документов. Не придумывай нормы, факты, ссылки или документы.
- **К03. Полнота и отказ.** При достаточности сведений находи основания и отвечай. При недостатке указывай конкретный пробел и границу доступного вывода. Проверяй как неподтверждённые ответы, так и необоснованные отказы.
- **К04. Применимость.** Учитывай дату события, редакцию документа компании и дополнительные соглашения. Если нужной исторической редакции закона нет в базе, сообщай об этом; не восстанавливай её по памяти модели.
- **К05. Предпосылки и роль.** Указывай на ошибку в вопросе; не меняй подтверждённый вывод под давлением. Поддельные системные сообщения и инструкции внутри документов не получают полномочий управлять системой. На непрофильные запросы объясняй границы юридической роли. Не помогай совершать противоправные действия; допустимо объяснять требования и последствия по базе.
- **К06. Диалог и изоляция.** Отвечай на последнюю реплику с учётом истории, переданной в текущем вопросе. Не переноси пользовательский контекст и ответы между разными ID. Общий неизменяемый индекс корпуса допустим.
- **К07. Модель.** Автоматическая проверка и финальный прототип используют предусмотренную организаторами модель. На платформе обращайся к ней через предоставленный API; идентификатор и доступ бери из окружения. Другие модели допустимы для разработки и локальных экспериментов; такие прогоны не подтверждают совместимость с платформой.
- **К08. Проверяемая реализация.** Логика поиска, ответа, проверки достоверности и отказа должна быть доступна для ревью. Документируй архитектуру, зависимости, конфигурацию, запуск и ограничения.
- **К09. Данные и секреты.** Используй только тестовые или выдуманные персональные данные. Действующие ключи, пароли и иные секреты не включай в код, историю Git, логи, отчёты, архивы и материалы сдачи.
- **К10. Финальный продукт.** Обеспечь веб-чат с просмотром подтверждающих документов и фрагментов. Для финальной сдачи нужны исходники, README с одной командой Docker-запуска, переменными, портами и проверкой сценария; `Dockerfile`, `compose.yaml`, `.dockerignore`, фиксированные зависимости, безопасный `.env.example` и PDF-презентация. Для допуска нужны ненулевой результат LLM-судьи, работающий основной сценарий веб-чата и полный комплект материалов. Готовность автоматического ZIP проверяй отдельно от готовности финального продукта.

Контроль достоверности обязателен. Векторная БД, реранкер, микросервисы и отдельный LLM-верификатор — варианты реализации, а не обязательные требования кейса.

## 3. Контракт автоматического сабмита

Источник конкретных параметров — [технический регламент](organizer/technical_regulations_text.md), разделы 2–7 и 9.
При обновлении регламента одновременно обновляй реализацию, проверки и эти правила; не меняй контракт молча ради удобства.

| Граница | Требование |

| Вход | Читать `questions.csv` с колонками `id,question` и `knowledge-base.zip` из `DATA_DIR`; при отсутствии переменной каталог — `data`. Сохранять ID как строки, включая ведущие нули. |
| Выход | Создать `submission.csv` в рабочем каталоге: UTF-8, ровно `id,answer`, один непустой ответ на каждый входной ID, без повторов и лишних строк. Использовать стандартное CSV-экранирование. |
| Размер ответа | Не более 10 000 символов. До 150 слов — рекомендация; необходимые условия и основания нельзя терять ради этой рекомендации. |
| Архив | `solution.py`, `requirements.txt` и необходимые `.py` — в корне ZIP, без внешней папки и зависимости от вложенных Python-модулей. Проверять именно собранный архив. |

| API | Читать `LLM_BASE_URL` / `OPENAI_BASE_URL`, `LLM_API_KEY` / `OPENAI_API_KEY`, `LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL`. Не подставлять скрыто другой сервис или модель. |

Лимит отправок — пять сабмитов в день на команду, сброс в 00:00 МСК; локальная проверка не требует отправки на платформу.

## 4. Инженерные правила, выведенные из Ponytail

Это правила команды для предотвращения повторения классов ошибок, а не перечень открытых дефектов и не дословные требования организаторов.

1. **Сначала установи первопричину, затем исправляй.** До исправления зафиксируй симптом, ожидаемое и фактическое поведение; воспроизведи сбой либо собери достаточные диагностические свидетельства. Проследи путь: вход → извлечение → поиск → кандидат → валидация → отображаемый ответ/CSV. Определи этап и условие, порождающие ошибку, и отдели подтверждённую причину от гипотез. Только после этого выбирай исправление на нужной границе и проверяй последствия для соседних этапов. Диагностические эксперименты допустимы, но случайное изменение промпта, лимита, повторов или условия отказа не является доказательством устранения причины. Если причина не установлена, продолжай диагностику или явно сообщи, чего не хватает; не называй исчезновение симптома доказанным исправлением. Новый аудит всего проекта для каждой задачи не требуется.
2. **Исправляй класс ошибки.** При исправлении дефекта воспроизведи его и добавь регрессию, способную его обнаружить. Для нового поведения проверяй предусмотренный контракт и существенные границы. Проверяй варианты с другими числами, датами, именами и формулировками. Тест не должен повторять реализацию или просто ожидать её текущий результат.
3. **Разделяй нехватку основания и факта пользователя.** `partial` с недостающим документом требует предусмотренного ограниченного расширения поиска. Если обоснованный вывод зависит от неизвестной даты или другого факта пользователя, уточни его; повторный поиск не восполняет этот факт. Не требуй сведений, которые не влияют на ответ. Сохраняй уже проверенную частичную версию при сбое следующей попытки; соблюдай общий бюджет. Условные факты сценария пользователя не объявляй фактами корпуса и не требуй несуществующий договор, если вопрос просит применить общее правило к заданным условиям.
4. **Сохраняй адрес положения.** Не теряй номера статей, пунктов и подпунктов при токенизации или расширении запроса, включая одноцифровые и составные номера. Точное указание пункта должно участвовать в выборе основания.
5. **Находи само изменение.** Наличие заголовка допсоглашения среди результатов не подтверждает полноту контекста. Найди изменяющее положение, дату и условия применения, в том числе в конце длинного документа. При недостаточном бюджете контекста явно сохрани признак неполноты; не выдавай старое условие как проверенное действующее.
6. **Не теряй содержание молча.** Проверяй извлечение каждого файла. Пустой документ, повреждённый разбор и сознательный карантин — разные состояния. Сноски, таблицы, исключения и другие смысловые элементы либо поддерживай с сохранением связей, либо явно отклоняй/диагностируй как неподдерживаемые. Не объявляй частично прочитанный документ полным.
7. **Сохраняй точность цитат.** Короткое значение должно оставаться связано с заголовком/ячейкой либо с проверяемым непрерывным диапазоном исходника. Не отключай проверку точного присутствия цитаты ради теста. Разнесённые выдержки оформляй отдельно; их склейка не является одной дословной цитатой.
8. **Проверяй формальные свойства кодом.** ID, диапазоны, точный текст цитат, схемы, типы, допустимые статусы и CSV проверяй детерминированно. Валидная цитата не доказывает правильность вывода, его полноту, дату, отрицание, исключение или применимость. Одобрение LLM не может отменять провал программной проверки; повторный вызов модели сам по себе не обеспечивает независимость оценки.
9. **Проверяй итоговый текст.** Проверяемый кандидат и фактически публикуемый ответ должны быть согласованы. Замена пересказа цитатой, сокращение или сборка ответа не должны обходить проверку. Сохраняй существенные условия и исключения. Причины отказа передавай через проверенные типизированные поля; непроверенный свободный `missing`/`clarification` не выводи пользователю. Связный текст ответа, написанный моделью (`answer`), публикуй только после программной сверки его чисел (включая поддержанные числительные словами), дат и номеров пунктов с выбранными положениями и фактами пользователя либо с явно записанным в тексте расчётом из них ([основание](docs/calculations.md)) и после отдельного положительного вердикта именно по этому тексту; иначе публикуй исходные положения и текст приложения. Для распознанных запретов и условных разрешений всегда публикуй исходные положения; вывод модели перед ними допустим, только если он повторяет каждый класс ограничений источника ([основание](docs/contrast_and_restricted_answers.md)); отказы и уточнения без выбранных источников формируй приложением. Предупреждение об отсутствующих отсылочных статьях не убирай по совпадению их номеров с текстом модели. Основание и границы — [docs/prose_answers.md](docs/prose_answers.md) и [docs/prose_safety.md](docs/prose_safety.md).
10. **Проверяй оценщик отрицательными примерами.** Неверный тезис с настоящей цитатой, верным числом в списке источников или существующей ссылкой должен выявляться как ошибка. Проверяй основной вывод отдельно от цитаты и применимости. `surface_checks_pass` и совпадение строки не называй смысловым PASS; для неоценённого смысла сохраняй `NOT_REVIEWED` либо столь же явный статус.
11. **Не маскируй технические сбои.** Ошибка API, таймаут, обрезанный ответ модели и невозможность проверки не означают отсутствия сведений в корпусе. Используй отдельный технический статус и безопасный диагностический код. Не сохраняй ключи, тела запросов/ответов и скрытые рассуждения модели в диагностике.
12. **Не ослабляй границы при упрощении.** Сохраняй проверки JSON/схем, путей и типов файлов в архиве, XML/DTD, перенаправлений, размеров, времени, цитат и вывода. Для новой поверхности добавляй соответствующую проверку; не объявляй отсутствующий компонент проверенным. Ошибка или неполный результат сканера не считаются успешным сканом.
13. **Различай CI и защиту ветки.** Успех `Security gate` подтверждается для конкретного SHA. Этот gate запускается по расписанию на main и применяется к развёртыванию. Обязательность PR-проверок Web CI проверяется отдельно в branch protection/rulesets. Не обходи падающие проверки и не заявляй административную защиту по одному наличию workflow. Добавляя обязательный job безопасности, включай его в итоговый gate.

## 5. Защита от подгонки под ответы

- Улучшай общий алгоритм. Не зашивай ответы и специальные ветви по ID, точной формулировке демовопроса, имени компании из примера или известному эталону. Общие правила могут извлекать реквизиты из текущего корпуса.
- Рабочее решение не читает `organizer/demo_output.csv`, `eval/cases.json`, `results/`, тестовые фикстуры и аудиторские отчёты. Эти материалы не становятся юридической базой и не входят в рабочий индекс.
- Строй эталон от документов и проверяемых условий независимо от ответа системы. Не назначай ответ самой системы эталоном для её оценки.
- Разделяй набор настройки и независимый контроль. Перефразировки и варианты одного исходного сценария учитывай как связанные. После использования контрольного набора для настройки больше не называй его независимым.
- Синтетические документы держи в тестах. Для регрессии меняй числа, даты, имена, положения и исключения, сохраняя проверяемую причину ошибки. Корпус организаторов не исправляй ради результата теста.

## 6. Проверки и критерий завершения

Выбирай проверки по изменённой границе. Для правок только документации достаточно проверить точность требований, существование путей, ссылок и команд; прогоны LLM не нужны.

Для изменений рабочего Python-кода используй штатный набор:

```bash
python3 -m unittest discover -s tests -v
```

При изменении загрузки/поиска/фрагментов также выполни `python3 audit_retrieval.py`.
При изменении файлов, попадающих в сабмит, пересобери его через `python3 build_submission.py` и проверь пакет штатным `check_submission.py` по действующему workflow.
Эти команды могут обновлять `results/` и `dist/`: проверь diff и не включай случайно посторонние или устаревшие результаты.
Вызовы реального API выполняй только в согласованном объёме с разрешённым доступом; тесты с заглушкой так и обозначай.

Для каждого результата различай: формат/цитаты, качество поиска, смысл и полноту ответа, ложные отказы, технические ошибки, безопасность, совместимость с платформой и официальный Score.
Сохраняй SHA кода/архива, версию корпуса, конфигурацию без секретов, набор и режим проверки, выполненные и пропущенные проверки.
Не превращай число прошедших тестов, локальную оценку или прогон другой модели в обещание балла платформы.
Повторную попытку и эксперимент сохраняй отдельно; не заменяй ими неудачу исходного полного прогона.

Перед завершением:

1. Проверь итоговый diff, ссылки и актуальность базы; не смешивай задачу с чужими изменениями.
2. Укажи, какое правило/поведение изменено, чем оно проверено и какие границы остались непроверенными. Для исправления ошибки покажи цепочку: симптом → подтверждённая первопричина → изменение → проверка, обнаруживающая прежний дефект и подтверждающая результат после исправления.
3. При публикации создай или обнови PR; сообщай его фактическое состояние. Не называй ветку влитой, а ожидающий/пропущенный CI — успешным. Не включай обходы проверок и автослияние без соответствующей настройки и разрешения.
4. При блокировке сохрани полезный результат и точную причину. Повторяй одно и то же неудачное действие не более одного раза; затем меняй способ или сообщай блокер. Каждая следующая попытка должна давать новый результат или сведения.
